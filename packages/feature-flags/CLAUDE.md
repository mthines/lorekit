# @lorekit/feature-flags

OpenFeature-standard flag evaluation. One hand-authored registry
(`src/registry.ts`), codegen'd into typed TS bindings and a language-neutral
manifest, resolved by `LoreKitFlagProvider` (static value, weighted A/B(/n)
experiment, or a session override — checked in that priority order), and
OTel-instrumented on both server-side spans and browser RUM.

→ **Full guide:** [`docs/feature-flags.md`](../../docs/feature-flags.md) — read
it before touching this package if you haven't already.
→ **Adding/updating/removing a flag:** use the `feature-flags` skill
(`.claude/skills/feature-flags/SKILL.md`) rather than hand-editing
`registry.ts` and remembering every step yourself.

## Rules

- **`registry.ts` is the only source of truth.** Never hand-edit
  `src/generated/flags.generated.ts` or `generated/flags.manifest.json` —
  both are regenerated by `node --experimental-transform-types
  scripts/codegen/gen-feature-flags.mjs`, and `nx run
  feature-flags:check:generate` (+ `generated-artifacts.spec.ts`) fails CI
  when they drift from the registry.
- **Always regenerate after editing the registry.** A registry change with
  stale generated files is a broken PR, not a lint nitpick — `FlagKey` /
  `FlagValueMap` in the generated file are what give every call site its
  type safety, and the manifest is the only artifact a future non-TS
  consumer would read.
- **`evaluateFlag`/`evaluateFlagDetails`/`getFeatureFlagClient` are the only
  call surface.** Never import `LoreKitFlagProvider` or call `OpenFeature.*`
  directly from application code — that indirection is the entire point of
  depending on OpenFeature (see `docs/feature-flags.md` § "Why OpenFeature").
- **A UI-affecting experiment's arms are separate components, never inline
  branches.** The copy-and-suffix convention
  (`ComponentName.tsx` resolver + `ComponentName.<variant>.tsx` per arm) is
  documented in `docs/feature-flags.md` § "UI variants". The live example is
  `packages/web/src/components/lore/DuplicateClustersPanel{,.on,.off}.tsx`
  (`lore-explorer-duplicate-clusters`) — copy its shape, including the `off` arm
  being a whole component that returns `null` and the arm being separate from the
  implementation it renders. Do NOT add an example that gates nothing just to
  demonstrate the pattern; that is what was removed (see `registry.ts`'s header).
  Reach for a plain `useFeatureFlag`/`getServerFlag` boolean read instead when a
  flag only gates one small prop or class, not a component's whole shape —
  `lore-explorer-instruments` is the reference for that lighter case.
- **Overrides select a VARIANT KEY, never a raw value.** `parseFlagOverrides`
  validates every override against the live registry (unknown flag, unknown
  variant → silently dropped) — never trust an override cookie's contents
  without going through it.
- **`object`-typed flags have no per-flag TypeScript shape.** Every `object`
  flag types as the generic `JsonValue` (`schema.ts`) — narrow it at the call
  site if you need a specific shape. See `docs/feature-flags.md` § "Value
  types" before proposing a per-flag payload schema as a first move.
- **`ANONYMOUS_TARGETING_KEY` in `provider.ts` is a last-resort fallback, not
  a design.** Every real caller must supply a stable `targetingKey` —
  `packages/web` does this via `lib/feature-flags/anon-id.ts`'s httpOnly
  cookie. A dev-mode console warning fires once per flag if this fallback is
  ever actually hit; treat seeing it as a real bug in the calling code, not
  noise to suppress.

## Adding a flag (terse version — the skill has the full checklist)

1. Add an entry to `REGISTRY_INPUT` in `src/registry.ts`.
2. `node --experimental-transform-types scripts/codegen/gen-feature-flags.mjs`
3. `nx test feature-flags` — the freshness spec re-verifies the regenerate,
   and add a test for anything beyond the schema's own validation (a new
   experiment's bucketing distribution, a new provider edge case).
4. If the flag drives a UI variant, scaffold the copy-and-suffix resolver +
   per-arm components (see `docs/feature-flags.md` § "UI variants") rather
   than adding a branch to an existing component.
5. `nx typecheck feature-flags web && nx lint feature-flags web`.

## Removing a flag

1. Delete every consumer — `grep -rn '<flag-key>'` across `packages/web/src`
   and this package. For a copy-and-suffix flag: promote the winning arm's
   file into the resolver's place, delete the losing arm's file(s), delete
   the resolver's dispatch logic.
2. Delete the entry from `registry.ts`.
3. Regenerate (step 2 above) and re-run tests/typecheck.
4. Grep the repo once more for the flag key (docs, `docs/feature-flags.md`
   examples, comments) — nothing should still reference it.

## File map

| File | Role |
|------|------|
| `src/schema.ts` | `FlagDefinitionSchema` (zod) — the validation every registry entry must pass; `JsonValue` — the recursive type `object`-typed flags accept |
| `src/registry.ts` | `REGISTRY_INPUT` — the hand-authored flags; `FLAG_REGISTRY` — the validated, canonical export |
| `src/bucketing.ts` | `assignExperimentVariant` / `fnv1aHash` — deterministic, stateless A/B(/n) bucketing |
| `src/overrides.ts` | `parseFlagOverrides`/`serializeFlagOverrides`/`withFlagOverrides` — the transport-agnostic session-override mechanism (the cookie itself lives in `packages/web`) |
| `src/provider.ts` | `LoreKitFlagProvider` — the OpenFeature `Provider`; resolution order is override → experiment split → static default |
| `src/client.ts` | `evaluateFlag`/`evaluateFlagDetails`/`getFeatureFlagClient` — the only call surface application code should use |
| `src/otel-hook.ts` + `src/otel-attributes.ts` | Server-side span instrumentation — `feature_flag.*` attributes per evaluation |
| `src/generated/flags.generated.ts` | GENERATED — `FlagKey` union, `FlagValueMap`, `FLAG_KEYS`. Never hand-edit |
| `generated/flags.manifest.json` | GENERATED — the language-neutral manifest for a future non-TS consumer |
| `scripts/codegen/gen-feature-flags.mjs` (repo root) | The generator — pure render functions + `--check` staleness mode |

`packages/web`'s half (server helpers, the `FeatureFlagsProvider` context,
the override cookie + Server Actions, RUM sync, the Developer settings page)
is documented in `docs/feature-flags.md` § "`packages/web` integration"
onward — not duplicated here.

## Tests

`nx test feature-flags` — Vitest, `src/**/*.spec.ts`. Every module has a
co-located spec; `generated-artifacts.spec.ts` is the freshness/idempotence
guard on the generated files (runs the generator as a subprocess in a
sandbox — see its own header comment for why it can't just `import()` the
generator directly).
