<TutorialCallout variant="info">

Claude Code on the web runs every session in a **fresh, ephemeral cloud container**: the repository is re-cloned when the container starts, and nothing you write to disk survives once the session ends. Two things follow from that, and they hold no matter which setup path you pick — use **remote mode** so your lore persists across sessions, and keep your token in the **`LOREKIT_TOKEN` environment variable** so it never lands in a file you commit.

</TutorialCallout>

**Why the local store is the wrong choice here**

The [offline store](/docs/offline) keeps memories as plain files under `.lorekit/`. In an ephemeral container those files are wiped when the session ends, so every session would start with an empty memory. Remote mode syncs to the hosted MCP server instead, so lore written in one session is available in the next — on any container, from any machine. This tutorial assumes [remote mode](/docs/remote).

## Shared setup

These three steps are the same whichever wiring path you choose below.

<TutorialStep number={1} title="Generate a read-write API token">

Go to [Settings → API keys](/settings/api-keys) and click **Generate new token**. Give it a name (e.g. `claude-web`) and choose the read + write tier (`lk_rw_…`) so agents in the web session can both read and record lore.

The token is shown **once only** — copy it before closing the modal.

</TutorialStep>

<TutorialStep number={2} title="Store the token as an environment variable">

In Claude Code on the web, each environment carries its own configuration — environment variables, secrets, and setup scripts (see the [environment docs](https://code.claude.com/docs/en/claude-code-on-the-web)). Add your token there rather than in the repo:

```bash
LOREKIT_TOKEN=lk_rw_<your-token>
```

This is the one secret, and it stays out of version control by living in the environment configuration. Both paths below read it from here — neither writes it into a file you commit.

</TutorialStep>

<TutorialStep number={3} title="Allow outbound network access">

The web environment routes outbound HTTPS through a proxy governed by the environment's **network policy**. LoreKit needs two hosts reachable:

- `pqokxlhvnosogizsjztg.supabase.co` — the hosted MCP endpoint
- `registry.npmjs.org` — so `npx` can fetch `@lorekit/cli`

If your environment uses a restricted network policy, add both hosts to its allowlist. A policy that already permits general HTTPS and npm needs no change.

</TutorialStep>

## Choose how to wire LoreKit in

There are two good paths. They connect the same account to the same hosted store — they differ only in **where the wiring lives**.

| | Install the CLI (Option A) | Commit a token-free config (Option B) |
| --- | --- | --- |
| Best for | Fastest setup, full experience | Reproducible config in version control |
| Where the wiring lives | Regenerated each session by a setup script | Committed `.lorekit.json` + `.mcp.json` |
| Lifecycle hooks (inject lore, nudge) | Yes, via `--hooks all` | Only if you also commit `.claude/` |
| Skills scaffolded | Yes | Only if you also commit `.claude/` |
| Needs setup-script access | Yes | No |
| Token | `LOREKIT_TOKEN` env | `LOREKIT_TOKEN` env |

If in doubt, use **Option A** — it is the same one-command install as on the desktop, and it wires the lifecycle hooks and skills that make lore surface automatically.

### Option A — Install the CLI in a setup script

Run the normal installer from the environment's **setup script** (or a `SessionStart` hook). Because the container is re-created each session, the install runs fresh each time; the container state is cached after the setup script, so the cost is paid once:

```bash
#!/bin/bash
set -euo pipefail

# One command: scaffolds the skills, wires the MCP server, and installs the
# lifecycle hooks. Non-interactive, safe to re-run.
npx -y @lorekit/cli install --hooks all --yes
```

What each part does, and why it is safe here:

- **No endpoint flag needed.** `install` defaults to the hosted MCP endpoint (`https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp`).
- **The token comes from `LOREKIT_TOKEN`.** `install` reads it from the environment — you never type or commit it. It is written only into the container's generated `.mcp.json`, which is thrown away when the session ends.
- **`--hooks all`** wires the SessionStart / failure / end-of-turn hooks so prior lore is injected and a retrospective nudge fires on failures. Hooks inject context; they never write memory themselves. Use `--hooks read-only` or `--hooks none` to change that — see [Offline storage](/docs/offline).
- **`--yes`** keeps it non-interactive (a setup script has no TTY, so this is belt-and-suspenders).

<TutorialCallout variant="tip">

`install` writes your token into the generated `.mcp.json`. That file must never be committed — add `.mcp.json` to `.gitignore`. In this flow it is regenerated from `LOREKIT_TOKEN` on every session, so there is nothing to keep in the repo.

</TutorialCallout>

### Option B — Commit a token-free config

Prefer the connection to live in version control (identical for every teammate, no setup-script access required)? Commit two small files, neither of which holds a secret.

First, a `.lorekit.json` at the repo root with the mode and endpoint:

```json
// .lorekit.json — repo root, safe to commit (no secrets)
{
  "mode": "remote",
  "mcp.endpoint": "https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp"
}
```

Then a `.mcp.json` that runs the CLI's own MCP server instead of embedding a token in a connection URL:

```json
// .mcp.json — repo root, safe to commit (no token)
{
  "mcpServers": {
    "lorekit": {
      "command": "npx",
      "args": ["-y", "@lorekit/cli", "mcp"]
    }
  }
}
```

`npx @lorekit/cli mcp` starts a local stdio MCP server that proxies `memory.*` (and `org.*`) tool calls to the hosted store. It reads the mode and endpoint from `.lorekit.json` and the token from the `LOREKIT_TOKEN` environment variable, so **the committed file carries no secret** — the key difference from `install`, which bakes the token into the connection URL.

<TutorialCallout variant="tip">

Option B connects the tools but does not scaffold the lifecycle hooks or skills. To get those too while keeping the config committed, run `npx @lorekit/cli install --hooks all` once locally, commit the generated `.claude/` directory, and **replace the generated `.mcp.json` with the token-free one above** (so no token ends up in the repo). See the [Configuration reference](/docs/config) for every field.

</TutorialCallout>

## Verify and confirm persistence

<TutorialStep number={4} title="Verify the connection">

From a session terminal:

```bash
npx @lorekit/cli doctor
```

Look at the **Remote** section — both checks must be green:

- **`connectivity`** probes the public `/health` function (proves the network path).
- **`authentication`** makes one authenticated request. A revoked or missing token fails here with HTTP 401 and `doctor` exits non-zero.

If `authentication` reports the token is rejected, regenerate it at [Settings → API keys](/settings/api-keys) and update the `LOREKIT_TOKEN` environment variable.

</TutorialStep>

<TutorialStep number={5} title="Confirm lore survives across sessions">

Have your agent write a memory in one session:

```json
memory.write {
  scope: "global",
  key:   "hello-cloud",
  value: "LoreKit is wired up in Claude Code on the web."
}
```

Start a **new** session and read it back:

```json
memory.read {
  scope: "global",
  key:   "hello-cloud"
}
// → { "value": "LoreKit is wired up in Claude Code on the web.", "updated_at": "…" }
```

Because the value comes from the hosted store, it survives the container being reclaimed — which is exactly what the local store could not do.

</TutorialStep>
