<TutorialCallout variant="tip">

You can use the hosted instance at `lorekit.io` or self-host your own. This tutorial uses the hosted instance. For self-hosting see the [Installation Guide](https://github.com/mthines/lorekit/blob/main/docs/install.md).

</TutorialCallout>

<TutorialCallout variant="tip">

**Using Claude Code, Cursor, ChatGPT or VS Code?** You can skip the token entirely. Add the server URL with no credential, press **Authorize** in your client's MCP list, and pick which organizations the connection may reach on the consent screen. See [Authorize instead of pasting a token](#authorize-instead-of-pasting-a-token) at the bottom of this page.

</TutorialCallout>

<TutorialStep number={1} title="Generate an API token">

Go to [Settings → API keys](/settings/api-keys) and click **Generate new token**. Enter a name (e.g. `claude-local`, `ci-prod`) and choose a permission tier:

- `lk_rw_…` — read + write (agents that learn)
- `lk_ro_…` — read only (CI context injection)
- `lk_wo_…` — write only (one-way memory feeders)

The token is shown **once only** — copy it before closing the modal.

</TutorialStep>

<TutorialStep number={2} title="Point your agent at the MCP server">

The fastest path is `npx @lorekit/cli install` — it scaffolds the skills, wires the MCP server, and installs the lifecycle hooks in one command. Or add the endpoint manually to your agent's MCP config:

```json
// .mcp.json (Claude Code / Cursor / opencode — project-local)
{
  "mcpServers": {
    "lorekit": {
      "command": "npx",
      "args": ["-y", "mcp-remote",
               "https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp",
               "--header", "Authorization:Bearer lk_rw_<your-token>"]
    }
  }
}
```

<TutorialCallout variant="tip">

Keep `.mcp.json` out of version control — it contains your token. Commit a `.lorekit.json` instead to set the team default mode (e.g. `{ "mode": "remote" }`).

</TutorialCallout>

</TutorialStep>

<TutorialStep number={3} title="Verify the connection">

```bash
npx @lorekit/cli doctor
```

The doctor command checks connectivity, token permissions, and scope health. Look for the **Remote** section in the output — it should show a green `ok` status.

Two of those checks answer different questions, and both must be green:

- **`connectivity`** probes the public `/health` function. It proves the network path only — it stays green for a token that no longer works.
- **`authentication`** makes one authenticated request and reports what the server said about the token. A revoked or deleted token fails here with HTTP 401, and doctor exits non-zero. A write-only `lk_wo_*` token passes with a note that it has no read permission.

<TutorialCallout variant="tip">

Seeing `authentication — token REJECTED`? The token was revoked or deleted. Generate a new one at [lorekit.io](https://lorekit.io), then run `npx @lorekit/cli install --force` — it asks whether to keep, replace, or remove the token already in your config.

</TutorialCallout>

</TutorialStep>

<TutorialStep number={4} title="Write and read a memory">

Write a test memory via the MCP endpoint:

```json
memory.write {
  scope: "global",
  key:   "hello-remote",
  value: "Remote lore is working."
}
```

Read it back from any machine:

```json
memory.read {
  scope: "global",
  key:   "hello-remote"
}
// → { "value": "Remote lore is working.", "updated_at": "…" }
```

</TutorialStep>

<TutorialStep number={5} title="Use in CI / GitHub Actions">

Store a read-only token as `LOREKIT_TOKEN` in your repo secrets, then inject global memories before any AI step:

```yaml
- name: Inject LoreKit context
  run: |
    curl -s -X POST "$LOREKIT_MCP_URL" \
      -H "Authorization: Bearer $LOREKIT_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/call",
        "params": {
          "name": "memory.list",
          "arguments": { "scope": "global", "limit": 20 }
        }
      }'
  env:
    LOREKIT_MCP_URL: https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp
    LOREKIT_TOKEN: ${{ secrets.LOREKIT_TOKEN }}
```

</TutorialStep>

<TutorialStep number={6} title="(Optional) Install the GitHub App">

To have LoreKit automatically learn from PR review comments, go to [Settings → Integrations](/settings/integrations) and install the LoreKit GitHub App. Every repository you grant it is covered instantly — there is no per-repo secret to copy and no webhook to configure on GitHub:

- **Covers:** every repo you grant the App, as you add or remove them on GitHub
- **Learns from:** resolved pull request review comments and reviews
- **Tags each memory:** `source::pr-webhook`

</TutorialStep>

## Authorize instead of pasting a token

Modern MCP hosts show an **Authorize** action next to a server that needs
authentication. LoreKit supports it, so on a machine you use interactively you
never have to generate or copy a token.

Add the server with no credential at all:

```json
// .mcp.json
{
  "mcpServers": {
    "lorekit": {
      "url": "https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp"
    }
  }
}
```

Then press **Authorize** in your client. Your browser opens the LoreKit consent
screen, where you choose two things:

- **Access level** — read + write, or read only.
- **Which lore** — your personal lore is always included. Each organization you
  belong to is a separate checkbox, unticked by default, so a connection only
  reaches the teams you deliberately give it.

<TutorialCallout variant="tip">

Unticking an organization hides it from that connection. And you never depend on
the checkbox alone: membership is re-checked on every request, so leaving an
organization revokes its access immediately even while the token still names it.

</TutorialCallout>

The resulting token shows up in [Settings → API keys](/settings/api-keys) named
after the client that asked for it, and is revoked there like any other. It
expires after 30 days; re-authorizing is the same one click and replaces the old
token rather than stacking up dead ones.

Keep using a generated token for CI and headless jobs — there is no browser
there to consent, and a CI credential should not expire mid-pipeline.
