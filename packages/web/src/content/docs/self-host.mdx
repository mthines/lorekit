## Compare the three setups

| | Hosted | Full self-host | Self-host + BYOD |
| --- | --- | --- | --- |
| What you run | Nothing | Your own Supabase project, all 8 Edge Functions | Your function project, plus a second Supabase project for storage |
| Where memories live | LoreKit's hosted project | Your project's own database | The second (storage) project's database |
| Dashboard / REST / hooks see your memories? | Yes | Yes | **No** — they all read the function project's own database, never the BYOD storage project |
| BYOD available? | No | N/A | Yes — layered on top of a full self-host deployment |

**Full self-host is the right default** unless your memory rows must live in
a separate database — data residency, an existing Supabase subscription
billed separately, or org policy. BYOD is never a substitute for deploying
your own function project; it only changes where rows are written, and the
hosted endpoint has no BYOD at all.

<TutorialStep number={1} title="Deploy your own backend">

Follow the [Installation Guide](https://github.com/mthines/lorekit/blob/main/docs/install.md)
on GitHub — it covers linking a Supabase project, applying migrations,
setting Edge Function secrets, deploying all 8 Edge Functions (not just
`mcp` + `health` — the `memories` function is required for hooks, the remote
CLI commands, and the dashboard's REST API), and generating an API token on a
dashboard connected to your project.

```bash
supabase link --project-ref <your-project-ref>
pnpm nx db:push supabase
supabase functions deploy --no-verify-jwt --project-ref <your-project-ref>
```

Verify with a health check:

```bash
curl https://<your-project-ref>.supabase.co/functions/v1/health
# → {"status":"ok","version":"1.0.0","db":"ok","ts":"…"}
```

</TutorialStep>

<TutorialStep number={2} title="(Optional) Bring your own database">

Only if your memory rows must live in a database you already run. Apply the
LoreKit schema to that second project and set `LOREKIT_STORAGE_URL` +
`LOREKIT_STORAGE_ANON_KEY` + `LOREKIT_STORAGE_SERVICE_KEY` as **Edge Function
secrets on your function project** (not in `.mcp.json` — that env never
reaches a deployed function). Follow the
[BYOD guide](https://github.com/mthines/lorekit/blob/main/docs/byod.md) for
the exact schema commands.

Remember: the dashboard, REST API, remote CLI commands, and hooks all read
the function project's own database. None of them see rows written to the
BYOD storage project.

</TutorialStep>

<TutorialStep number={3} title="Point your agent at your endpoint">

One endpoint setting covers MCP, REST, hooks, and the remote CLI commands,
because the CLI derives the REST base from the MCP endpoint:

```bash
npx @lorekit/cli install \
  --endpoint https://<your-project-ref>.supabase.co/functions/v1/mcp \
  --token    lk_rw_<your-token>
```

(or export `LOREKIT_MCP_URL` instead of passing `--endpoint` every time —
`install` reads only `--endpoint`, then `LOREKIT_MCP_URL`, then
`LOREKIT_ENDPOINT`. A committed `"mcp.endpoint"` in `.lorekit.json` is never
read by `install`. The remote CLI commands and hooks check the project's
`.mcp.json` first, then the global `~/.claude.json`, and use `mcp.endpoint`
only when neither has a LoreKit entry. A leftover hosted
`install --global` entry in `~/.claude.json` therefore still wins over a
committed `mcp.endpoint`, so re-run the global install with `--endpoint` too.)

<TutorialCallout variant="warning">

Re-running `npx @lorekit/cli install` **without** `--endpoint` rewrites the
MCP entry back to the hosted URL. Always pass `--endpoint`, or export
`LOREKIT_MCP_URL` in your shell profile, on every subsequent install.

</TutorialCallout>

</TutorialStep>
