## We watched one bot eat 13 of 15 slots

Here's the moment the old design died.

LoreKit injects the lessons your agent has learned at the start of a session. The first version capped that at 15 — a clean number, and completely wrong. On an active repo we watched a single self-improvement loop — the PR-review bot writing its own `loop::review-outcomes` bookkeeping — take **13 of the 15 slots**. The other two? The same lesson three times: `review-outcomes::pr395-it3`, `…it4`, `…it5`. One task's iteration log, injected as if it were three lessons.

The agent didn't get 15 lessons. It got one bot's diary and a stutter 😂

The bug wasn't the number. It was treating injection as *how many* instead of *which ones*. Cap-at-15 answered the wrong question, and it answered it twice badly: it was a **floor** as much as a ceiling, so a repo with six lessons got padded and a repo with six hundred got truncated — silently, with no way to tell which had happened.

So we rebuilt the read. What lands in your context now is a **ranked working set**: a slice of your window, spent on the highest-signal lessons, de-duplicated, warmed by what you're working on, and honest about what it left behind.

## "15 of what?" — spend a budget, not a count

Start with the number that replaced the number. There is no `MAX_LESSONS` anymore. The block spends a **character budget** — `hooks.sessionStart.maxChars`, default **1500** — because that's the thing that actually matters: how much of the window the block occupies. Fifteen terse keys and fifteen paragraph-long ones differ by an order of magnitude in cost, and "15" said nothing about either.

Characters, not tokens, on purpose — a real tokenizer is a dependency this package won't take, and ~4-chars-per-token is accurate enough to bound an order of magnitude. A second bound, `HARD_LESSON_CEILING = 40` lines, sits well above any sane budget so it never binds in normal use — it just stops a store of 500 one-word keys from rendering an unreadable wall.

The count falls out of the budget. That's the inversion: you decide how much window to spend, and the ranking decides what to spend it on.

## The read is ranked, not recent

Precedence still runs first — a `project::` lesson shadows the `global::` one of the same name, because that's a correctness rule, not a preference. But among the survivors, the old code took whatever order the read happened to hand it, which is *recency within a scope*. On an active repo the newest cluster is one task's iteration log — which is exactly how a dozen near-identical one-offs took the whole budget and evicted the lessons you'd re-learned all month.

Now we score the survivors. The score is a normalized blend of four factors, not a timestamp:

```js
// packages/cli/src/lessons-pure.mjs (shape of scoreWithTerms) — every factor in [0,1], weights normalized (default: all equal)
const score =
  (w.recency   * recencyFactor(entry.updatedAt, now, 14 /* -day half-life */) +
   w.salience  * salienceFactor(seenCount, maxSeenCount) +  // how often it recurred
   w.relevance * relevanceFromTerms(entry, branchTerms) +   // does it match what you're on?
   w.outcome   * normalizeOutcome(entry.outcome))           // did applying it help? (0.5 when unknown)
  / total;
```

Recency is one factor now, decaying on a two-week half-life — not the sort order. **Salience** is recurrence: a lesson you've re-learned five times outranks a fresh one-off, which is the whole point of writing lessons down. **Outcome** nudges toward lessons that actually helped, with a cold-start prior of `0.5` so a brand-new lesson isn't buried for lacking a track record. The budget goes to what's been *earned*, wherever it lives.

## It's warmed by what you're working on

Here's the part the first version couldn't do, and the objection it used to concede. At session start there's no task yet — so how can the read be relevant to anything?

It reads your **branch name**. A session on `feat/embedding-pipeline` distills the terms `embedding`, `pipeline` and lifts on-topic lessons up the ranking:

```js
// A relevance query from the branch NAME — owner/repo stripped, trunk names ignored.
const rankOpts = sessionRankOpts(scope, now, { branchHint: true });
```

It's a nudge, and a safe one: relevance only ever *lifts* an on-topic lesson — a non-match scores zero, so a branch that matches nothing (a bare `main`, a detached `HEAD`) doesn't reorder anything and you're back to recency-plus-salience. Cheap, deterministic, and it means the opening set already leans toward the thing you opened the editor to do. `hooks.sessionStart.branchHint` turns it off if you'd rather it didn't.

## No wall of duplicates

Ranking answers "which score highest." It does not answer "are these the same lesson." On an active repo the top-scoring cluster is often one task's `it3/it4/it5` rows — they score alike *and read alike*, so a plain top-N hands the reader the same thing several times and evicts the variety underneath.

So after ranking, we diversify the set with **MMR** — Maximal Marginal Relevance, Carbonell & Goldstein 1998 — at λ=0.7:

```js
// packages/cli/src/core/lessons.mjs — rank, un-flood, de-duplicate.
const ranked  = rankLessons(winners, rankOpts);
const capped  = capPerBucket(ranked, { cap: loopCap, bucketOf: loopBucketOf });          // loopCap=2 · the 13-of-15 fix
const lessons = diversifyRankedLessons(capped, { ...rankOpts, k: HARD_LESSON_CEILING });  // 40 · the stutter fix
```

MMR seeds with the top-ranked lesson (it's still 70% of the objective, so the best lesson stays first) and spends the other 30% pushing down anything that repeats what's already shown. The `it3/it4/it5` stutter collapses to one line, and the slot it freed goes to the next distinct thing.

That `capPerBucket` line is the 13-of-15 fix: no single self-improvement loop may take more than **2** slots. Those lessons are a bot's private working memory — read back by that bot through a tag filter — so two of its best surface and the rest step aside. General, human-written lessons are **never** capped; they're what the freed slots are for. (`hooks.sessionStart.loopCap`, default 2; set it to 0 to exclude bot buckets entirely.)

## It tells you what it left out

The old header reported only what it rendered, so a truncated block was indistinguishable from a complete one — the agent had no idea whether reaching for `memory.search` was worth it. The new header says `8 of 50`, and in the default `hybrid` shape it appends a scope map of where the other 42 live:

```text
LoreKit: 8 of 50 memories loaded · repo::mthines/lorekit — considerations, not rules; read any in full with memory.read.
- (repo::mthines/lorekit) supabase-rls::empty-array-is-not-no-rows — RLS returns 200 + [], not a 4xx…
- (global) always-typecheck-before-done — run the typecheck before you claim it's done
- … 6 more, ranked and de-duplicated, inside the budget …
More lore: branch::…/feat/x 3 · repo::mthines/lorekit 34 · global 13 — memory.search or memory.read to drill in.
```

(That block is illustrative — the shape `formatLessons` produces, not a single capture.) The counts are exact even on a huge store: they come from the store's own scope inventory — a Postgres aggregate on the hosted side, a tree walk locally — not from the bounded read, so a scope holding 400 lessons reports `400`, not a hand-wavy `25+`. Truncation is now self-describing: the agent can see there's more and go get it.

## The second gear: relevance when you fail

The ranked working set is the always-on gear. There's a sharper one that only engages when your agent hits a wall — a tool call fails — because that's the one moment it knows *exactly* what to search for. LoreKit distills terms from the error, runs one query across your scopes, and drops in up to three prior lessons before the retry. This one's real, unedited — a `git clone` failed while I was writing this post:

```text
LoreKit: 3 related memories — you've hit something like this before (considerations, not rules; read in full with memory.read):
- (global) implement-suggestion-lessons::negative-source-scan-assertions-must-be-mutation-verified — A negative source-scan assertion is unverified until you make it fail
- (global) reviewer-lessons::skill-dispatch-unavailable-is-not-skill-not-installed-read-the-symlinked-skill-md — A `Skill()` call the sub-agent cannot dispatch does NOT mean the skill is missing — the skill is on disk and must be READ instead, through…
- (global) reviewer-lessons::rebased-branch-makes-prior-sha-compare-useless-as-an-incremental-delta — A rebased PR branch makes `compare/PRIOR_SHA...HEAD_SHA` meaningless, and the harvest heuristic reads the resulting garbage as if it were…
```

And I'll be honest about *why* those three: the matcher is lexical, not semantic. That error said "could not read Username" — and two of those lessons literally contain "read." It matched on the shared word, not the meaning. No bullseye, no magic — a bounded ranked set up front, a targeted search the moment you trip.

## What it doesn't do

Let me be straight about the edges, because the design has them.

- **The ranking is lexical, not semantic — no embeddings on the read path.** Recurrence, recency, outcome, and word-overlap with your branch. There *is* a dormant embedding pipeline in the repo now, but it's off by default and semantic search isn't built — so a genuine paraphrase can still miss, the same trade as before. The read stays deterministic: no vector index, no re-embedding bill, no drift.
- **"Relevant" means your branch name, not your task.** It's a coarse hint — `feat/embedding-…` lifts embedding lessons — not your actual prompt or the file you just opened. A well-named branch helps; a branch called `wip` does nothing.
- **The budget is characters, not tokens.** A ~4-chars-per-token heuristic, deliberately. It bounds an order of magnitude, not a precise token count.
- **Precedence still owns correctness; ranking only orders the survivors.** A shadowed lesson can't score its way back into the set — so if the wrong copy is winning, that's a scope problem, not a ranking one.

None of these are things I'd rather you found at 2am.

## See it for yourself

Wire up the loop and start a session. The first thing you'll see is the header telling you how much of your lore it spent the budget on — `8 of 50` — and a scope map pointing at the rest. That one line is the whole philosophy: a ranked slice, and an honest pointer to everything it didn't show you.

Want a bigger or smaller slice? There's a single dial:

```bash
# ~/.lorekit.json or the repo's config
{ "hooks.sessionStart.maxChars": 2500 }
```

Spend more window, get more lessons — still ranked, still de-duplicated, still never flooded by one bot. That's the whole idea. 🙂
