## Count the memory formats on your machine

Here's a small exercise. List every place your coding tools keep something they "remember".

A typical setup today looks like this:

- an `AGENTS.md` or `CLAUDE.md` in most repos, and `.cursor/rules/*.mdc` in a few
- an API agent writing files to a `/memories` directory
- Copilot keeping facts about each repo on GitHub's side
- a memory MCP server keeping a JSONL knowledge graph

That's five or six shapes, and **none of them can read the others**.

Each one is reasonable on its own. Together, they're an industry rebuilding the same small idea again and again: *a note an agent left for its future self, stored at some address, true for a while.* A lesson your CI agent learns stays in whatever wrote it. Your editor agent can't read it. Neither can the next tool you try.

I build one of these tools, LoreKit, which is open source. So I'll be clear about what this post is and isn't. It isn't a pitch that LoreKit has solved memory. LoreKit's format is one proposal, and later in the post I'll list where it falls short. The point of the post is that **this is the moment to agree on a shared shape**, and that we've watched another field get this right.

## We've seen this before

Ten years ago, observability looked a lot like agent memory does now. Every monitoring vendor shipped its own agent, its own instrumentation library and its own data format. If you instrumented your code for one vendor, switching meant doing it again. Two open projects tried to fix this from different directions: OpenTracing (a common API) and OpenCensus (Google's instrumentation libraries and exporters). For a while they competed too.

In 2019 they merged into **OpenTelemetry**. The important part wasn't the code. It was what the vendors agreed to stop competing on. OpenTelemetry standardised four layers:

1. **A data model**: what a span, a metric and a log record are.
2. **Semantic conventions**: shared names like `service.name`, `http.*` and `db.*`, so the same thing is called the same thing everywhere.
3. **A protocol**: OTLP, one way to send the data.
4. **Reference implementations**: SDKs and the Collector, so nobody had to start from zero.

Vendors kept competing, but on what they *do* with the data: storage, querying, analysis, user experience. Users got to instrument once. I work with OpenTelemetry every day at [Dash0](https://www.dash0.com), and that one agreement is why a whole ecosystem of tools can read each other's data today.

Agent memory is at the stage observability was in before 2019. There are many formats, a few early proposals and no agreement. The timing is good for two reasons. The formats are still young enough to change. And the agent ecosystem already has a neutral home for shared standards: MCP and `AGENTS.md` both now sit under the Linux Foundation's Agentic AI Foundation.

## A tour of the shapes

To agree on a shape, it helps to see the ones we already have. These change quickly, so treat the details as a snapshot from late 2026.

| Family | Example | The unit of memory | Addressed by | Forgetting |
| --- | --- | --- | --- | --- |
| Instruction files | `AGENTS.md`, `CLAUDE.md`, Cursor `.mdc` rules | A whole Markdown file | File path (plus `globs` for Cursor) | Never. A person edits it |
| Agent-managed files | Anthropic's memory tool | A file under `/memories` | A path the model picks | Never, unless the model deletes it |
| Hosted repo facts | GitHub Copilot Memory | A fact with code citations | One repository | Deleted after 28 days unused |
| Context blocks | Letta core memory | A labeled block with a character `limit` | A `label` on an agent | Never. Always in context |
| Extracted facts | Mem0 | A fact the service extracts from messages | `user_id` / `agent_id` / `run_id` / `app_id` | Optional expiration date |
| Namespaced store | LangGraph `BaseStore` | A JSON `value` dict | A `namespace` tuple + `key` | Optional TTL, reset when the item is read (by default) |
| Knowledge graph | MCP reference memory server | Entities, relations, observations | Entity name | Never |
| Temporal graph | Graphiti / Zep | A fact on a graph edge | Entities + edge | Facts are invalidated rather than deleted, on two timelines |
| Addressed record | LoreKit | A record with a scope, key and lifecycle | A scope string + `key` | Never, unless a TTL is set |

Each of these got something right that a shared spec should keep:

- **Instruction files keep a person in the loop.** `AGENTS.md` is the closest thing to a standard here because it's simply a Markdown file at a known path. But it holds *rules a person curates*, not lessons an agent writes as it goes. It can't tell you how often something recurs, nothing in it expires, and it can't target anything finer than a directory.
- **Anthropic's memory tool proves plain files go a long way.** The model gets six commands (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`) under a `/memories` prefix, and your application decides where the files live. It's very portable. The cost is that two agents writing to the same directory have no shared idea of what a file *means*.
- **Copilot Memory checks itself against the code.** Every fact carries citations, which are links to specific code locations, and Copilot checks them against the current branch before using the fact. Facts disappear after 28 days without use. Of everything here, that pairing of *provenance you can check* and *forgetting by default* is the design I'd most like a shared spec to have. Today it's locked inside one product.
- **Letta treats memory as context budget.** A block has a `label`, a `value` and a character `limit`, and it's compiled into the prompt on every step. The format is honest that memory costs tokens every turn.
- **LangGraph shows how small the core can be.** It's `put(namespace, key, value)`, where the namespace is a tuple such as `("memories", user_id)`. Its optional TTL resets whenever an item is read.
- **The graphs model the world, and they model time.** The MCP reference server keeps entities, relations and observations in one `memory.jsonl` file. Graphiti stores four timestamps on every edge (`valid_at`, `invalid_at`, `created_at`, `expired_at`), so it can answer "what was true in March?" and keep a record of what replaced what.

### The proposals that already exist

Several people have already started on this. MacPaw Research has proposed **Portable Memory**, a `.mem` bundle with byte-reproducible serialization, deletion tombstones and optional signing. Its own authors say it's not yet widely adopted. The **Open Memory Protocol** is an April 2026 draft for moving conversations, and the memories derived from them, between platforms as a ZIP file with a manifest. Cognee offers a **COGX** exchange format with importers from Mem0, Letta and Zep.

These are starting points, not competitors. They mostly solve **export**: "how do I move my memory from vendor A to vendor B?" That matters most for personal assistants. Coding tools have a second problem that's still open: **live addressing**. When a CI job, an editor agent and a review bot work in the same repo at the same time, how do they write to and read from the *same* place, and agree on what it means? A complete spec needs both, the way OpenTelemetry needed both a data model and a protocol.

## What every format already agrees on

Strip away the branding and almost every format answers the same four questions, just in different ways:

1. **Where is this true?** A path, a repo, a user ID, a namespace tuple, an entity.
2. **What is its identity?** Something that decides whether a second write is an *update* or a *duplicate*.
3. **What does it say?** Almost always plain text, or JSON when a program is the reader.
4. **When does it stop being true?** Often skipped. When it isn't, the answers range from "28 days unused" to "two full timelines".

That's the part I find hopeful. These four questions are the beginning of a data model, and nobody disagrees that they matter. The tools only disagree on the answers. OpenTelemetry started from a similar place: everyone already had spans, they just shaped them differently.

There's one real fork. **Who writes the memory?** In instruction files it's a person. In the memory tool, Letta and LoreKit, the model writes directly. In Mem0 and Graphiti, a service extracts facts from the conversation. A shared format doesn't need to pick one. It needs to *record* which one, so a reader knows how much to trust what it reads.

## One proposal: LoreKit's record

Here is how LoreKit answers the four questions, offered as one data point. The full rationale for each column is in [an earlier post](/blog/agent-memory-data-model). Everything here, including the schema and the scope validator, is MIT-licensed in the repo.

- **Where: a scope string.** One of `global`, `project::{name}`, `repo::{owner}/{repo}` or `branch::{owner}/{repo}::{branch}`, read from most specific to least. Unlike LangGraph's tuple, it's a string with a grammar, so it means the same thing in a URL, a filename, a CLI flag or a log line. The separator is `::` because `/` already appears inside repo and branch names, and git doesn't allow `:` in a branch name.
- **Identity: `scope` + `key`, and a rewrite is counted.** Writing the same `scope` + `key` again updates the record and increments `seen_count`. One record that knows it was learned five times is more useful than five near-duplicates. But `seen_count` measures how often something came up, not whether it's true.
- **Body: plain text, read as advice.** The value is text up to 64 KiB, and LoreKit labels lessons *"considerations, not rules"* when it shows them to an agent. A rule belongs in `AGENTS.md`, decided by a person. A lesson is something an agent *noticed*, and it should be easy to ignore when it's wrong.
- **Lifecycle: permanent unless a TTL is set.** A write can carry `ttl_days`. Each later write that also carries one restarts the countdown, and a read never extends anything. Copilot and LangGraph made different choices here, and the figure below shows all three.
- **Kind: a short, closed list.** `lesson` (read every run), `bus` (a transient outcome, read only when deciding what to promote) and `signal` (a durable filter for one repo). This keeps records that serve different purposes from crowding each other out of an agent's context.
- **On disk: one Markdown file per record.** The frontmatter mirrors the hosted record's columns, with every value JSON-encoded so the file stays valid YAML and easy to grep.

## Where LoreKit's format falls short

If I hold LoreKit's record up against the other formats and against what OpenTelemetry got right, I find seven gaps. Each one maps to a failure I can point to. I'd make these changes whether or not a shared spec ever happens, and I'd want a shared spec to include them.

1. **No stable ID that's separate from the address.** A record's identity *is* its `scope` + `key`. So moving a lesson from a branch to the repo, or renaming its key, turns it into a different record. Everything that pointed at it, like the citations agents write when a lesson helped them, now points at nothing. OpenTelemetry gives every span an ID that doesn't depend on its name. Memory records need the same: a stable `id`, plus the address as a field that can change.
2. **No place for other tools' data, and rewrites lose it.** LoreKit has a fixed list of fields. When it rewrites a local file, any field another tool added is dropped. OpenTelemetry's answer is an open map of **attributes**, with shared names agreed through conventions. A memory record should have the same: an `attributes` map, namespaced keys like `ci.run_url` or `vcs.commit`, and a rule that a reader keeps keys it doesn't understand.
3. **The body doesn't say what it is.** LoreKit stores CI state as JSON inside the text value, and a reader can only tell from conventions like `kind: bus`. A `content_type` field (`text/markdown`, `application/json`) would let any reader know whether to show the body or parse it.
4. **Provenance says where a lesson came from, not what it depends on.** `origin_commit` records the commit a lesson was written on. It doesn't say which code the lesson is *about*. Copilot shows the better design: **anchors** (a file path, a line range, a commit and a content hash) that a reader *may* check. If the code under an anchor has changed, the lesson is flagged as possibly stale instead of being used blindly. That's the strongest protection against stale memory I've seen.
5. **The expiry rule is implicit.** Permanent-unless-a-TTL-is-set is a LoreKit default you have to know about. A record should state its rule: what extends its life (a write, a read, or use), and when it was last used. That makes the Copilot, LangGraph and LoreKit approaches different values of the same field, not three incompatible systems.
6. **Corrections leave no trail.** When a lesson turns out to be wrong, LoreKit's options are to overwrite it or archive it. A `supersedes` link from the new record to the old one would keep the history. You'd get the useful part of Graphiti's timelines without needing a graph.
7. **The address grammar assumes GitHub, and nothing says which version a file uses.** `repo::` accepts exactly `owner/repo`, so a GitLab path like `group/subgroup/repo` or a self-hosted server doesn't fit, and monorepos have no level between `repo` and `branch`. Records also carry no format version, so a future reader can't tell which rules a file was written under.

Here's a sketch of what a record could look like with those changes. It's an illustration, not a spec:

```yaml
---
spec: "agent-memory/0.1"                      # format version (7)
id: "01JC7Z3K9V2Q8M4T6R1W5X0YAB"               # stable, independent of the address (1)
scope: "repo::github.com/acme/checkout"        # host-qualified address (7)
key: "tests-need-local-postgres"
kind: "lesson"
content_type: "text/markdown"                  # (3)
written_by: { type: "agent", name: "claude-code" }
created: "2026-10-02T09:14:00Z"
updated: "2026-11-04T16:41:12Z"
seen_count: 4
lifecycle: { expires_at: "2026-12-04T16:41:12Z", extended_by: "write", last_used: "2026-11-06T08:02:51Z" }  # (5)
anchors:                                       # (4)
  - { path: "docker-compose.yml", lines: "12-20", commit: "0f4a1c9", sha256: "9b1e…" }
supersedes: null                               # (6)
attributes:                                    # open, namespaced, kept on rewrite (2)
  vcs.pr: 482
  ci.run_url: "https://github.com/acme/checkout/actions/runs/123456789"
---
Integration tests need Postgres up first: docker compose up -d db.
```

None of this is new. Every item is borrowed from a format in the table or from OpenTelemetry. That's the point: the pieces already exist, spread across tools that can't read each other.

## A test any shared format should pass

One test has convinced me the shape is general enough: can it hold memory that **no model wrote**?

CI jobs need memory too. A test workflow wants to know which tests were flaky last time. A deploy job wants the last SHA it shipped. Usually that goes into `actions/cache` or an artifact bucket nobody else reads. LoreKit stores it in the same record as a lesson, with a versioned JSON body:

```json
{
  "v": 1,
  "updated_by_run": "https://github.com/acme/checkout/actions/runs/123456789",
  "commit": "0f4a1c9",
  "data": { "flaky": ["src/queue.test.ts::retries on 429"], "consecutive_green": 3 }
}
```

```bash
RUN_URL="${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}"

jq -nc --arg run "$RUN_URL" --arg sha "$GITHUB_SHA" --argjson data "$NEW_DATA" \
  '{v: 1, updated_by_run: $run, commit: $sha, data: $data}' \
| npx @lorekit/cli write \
    --scope "repo::${GITHUB_REPOSITORY}" --key 'ci-state::flaky-tests' \
    --tags 'ci::test-state' --kind bus --host ci \
    --ttl-days 7 --remote --json
```

The same address, identity and lifecycle carry over. The job writes one key per fact and overwrites it in place, never one key per run. Because the job passes `--ttl-days 7` on every run, the expiry measures how long the job has been *silent*: the state lasts while the job runs and disappears a week after the workflow is deleted. And an agent asked to "fix the flaky tests" reads the same key and starts from the real list.

This is also where gaps 2 and 3 above hurt most. The JSON is only recognisable through conventions (`kind: bus`, a `v` inside the body). With `content_type` and `attributes`, any tool could read it. ## What a shared spec could look like

If agent memory followed OpenTelemetry's path, the spec would have the same four layers:

- **A data model.** One record: an address, a stable ID, a body with a content type, a lifecycle, provenance with optional anchors, a kind, and an open attribute map. Small enough that a shell script can write a valid record.
- **Conventions.** Shared names for address levels (`global`, `project`, `repo`, `branch`, and whatever monorepos need), for kinds, and for attribute namespaces (`vcs.*`, `ci.*`, `agent.*`). OpenTelemetry's semantic conventions are the model: one registry, versioned, open to anyone.
- **A contract.** A small set of memory operations (write, read, list, search, archive) with fixed inputs and outputs, exposed over MCP. Every memory server today speaks MCP but exposes different tools, so agents can call any of them and none of them mean the same thing.
- **Conformance tests.** Round-trip a record and check nothing was lost. Check that unknown attributes survive a rewrite. Check that expiry rules behave as stated.

What stays *out* of the spec matters as much: storage, ranking, embeddings, whether a model or an extractor writes, the user interface. Those are where tools should compete, the way observability vendors compete on everything after the data arrives.

The spec should live somewhere neutral, not in LoreKit's repo or any single vendor's. The Agentic AI Foundation already looks after MCP and `AGENTS.md`, which makes it one natural option, though that's for the people involved to decide.

## What a skeptic would say

These are the objections I'd raise if someone else had written this post.

**"You build a memory tool, so of course you want a standard shaped like it."** That's a fair suspicion. It's why this post lists LoreKit's gaps, and why the sketch above changes LoreKit's own format in seven places. If a shared spec ends up looking different, LoreKit should adopt it anyway. Being the tool that wrote the spec matters less than being one of many tools that can read each other's memory.

**"MCP already is the standard."** MCP standardises the *call*, not the *record*. It's like having a shared network protocol without a shared data model. OpenTelemetry needed OTLP *and* the data model. Memory needs both too.

**"Just use files in git."** For one person and one tool, files work well. The memory tool and LoreKit's offline store are both files. What plain files lack is agreement on what a file *means*: what it applies to, whether it repeats an earlier lesson, and when it stops being true. Frontmatter is a good place for that agreement to live.

**"Shared memory is a prompt-injection channel."** Yes. Anything an agent reads can steer it, and shared memory widens who gets to write those things. A spec should make the risk visible rather than hide it: record who wrote each memory and how, let readers check anchors, and allow signatures, which Portable Memory already proposes. No format makes poisoning impossible.

**"Another standard won't fix fragmentation."** That's the xkcd 927 problem: an attempt to unify everything adds one more competing standard. It's the strongest objection. My answer is the OpenTelemetry one. Agreement happened there when the existing projects *merged*, not when someone added a fifth. The useful work here is the same: take what Portable Memory, the Open Memory Protocol, Copilot, Letta, LangGraph and LoreKit each got right, and agree on one shape for the parts they share.

**"It's too early. Memory designs are still changing."** Maybe. But OpenTelemetry's data model has kept evolving since 2019, through versioning and conventions. Agreeing on a small core now doesn't freeze anything. It just stops every new tool from inventing its own core from scratch.

## Open questions

I don't know the answers to these, and I'd rather work them out in public:

- **Which address levels?** Monorepos want a level between `repo` and `branch`, and organisations want one above `project`. Is a fixed list right, or should levels be conventions too?
- **Should forgetting be the default?** Copilot forgets by default, LoreKit doesn't, and LangGraph extends life on read. A per-record rule avoids choosing, but tools still need a default.
- **Do coding lessons need two timelines?** Graphiti's case is strong for facts about the world. Is there a coding case where "what was true in March" matters?
- **Are anchors part of the core?** They're the best protection against stale memory, but they tie a record to a code host.
- **Who should coordinate?** A working group across tool builders, a foundation, or a draft spec that people send changes to?

If you build any of the tools in the table, or you've written one of the existing proposals, I'd like to compare notes. Disagreement is the useful part. LoreKit's schema, scope validator and on-disk format are in the repo as one concrete input to that conversation.
