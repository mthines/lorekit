## Count the memory formats on your machine

Here's a small exercise. List every place your coding tools keep something they "remember".

A typical setup today looks something like this. There's an `AGENTS.md` or `CLAUDE.md` in most repos, plus `.cursor/rules/*.mdc` in a few. An API agent writes files to a `/memories` directory. Copilot keeps facts about each repo on GitHub's side. A memory MCP server keeps a JSONL knowledge graph. That's five or six shapes, and **none of them can read the others**.

Each one is reasonable on its own. Together, they're an industry rebuilding the same small idea again and again: *a note an agent left for its future self, stored at some address, true for a while.*

I build one of these formats, so take this with that in mind. Here's what this post covers:

- a tour of the formats out there
- what they quietly agree on
- why LoreKit's record looks the way it does, including the parts I'm not sure about
- one test I think any open format should pass: can it hold memory that **no model wrote**?
- what a skeptic would say about all of this

## A tour of the shapes

Here are the families I've found. They all change quickly, so treat the details as a snapshot from late 2026.

| Family | Example | The unit of memory | Addressed by | Forgetting |
| --- | --- | --- | --- | --- |
| Instruction files | `AGENTS.md`, `CLAUDE.md`, Cursor `.mdc` rules | A whole Markdown file | File path (plus `globs` for Cursor) | Never. A person edits it |
| Agent-managed files | Anthropic's memory tool | A file under `/memories` | A path the model picks | Never, unless the model deletes it |
| Hosted repo facts | GitHub Copilot Memory | A fact with code citations | One repository | Deleted after 28 days unused |
| Context blocks | Letta core memory | A labeled block with a character `limit` | A `label` on an agent | Never. Always in context |
| Extracted facts | Mem0 | A fact the service extracts from messages | `user_id` / `agent_id` / `run_id` / `app_id` | Optional expiration date |
| Namespaced store | LangGraph `BaseStore` | A JSON `value` dict | A `namespace` tuple + `key` | Optional TTL, reset when the item is read (by default) |
| Knowledge graph | MCP reference memory server | Entities, relations, observations | Entity name | Never |
| Temporal graph | Graphiti / Zep | A fact on a graph edge | Entities + edge | Facts are invalidated rather than deleted, on two timelines |

Several of these made a choice the others didn't, and those choices are worth looking at.

**Instruction files keep a person in the loop.** `AGENTS.md` now sits under the Linux Foundation's Agentic AI Foundation, next to MCP. It's the closest thing to a standard here because it's simply a Markdown file at a known path. But it holds *rules a person curates*, not lessons an agent writes as it goes. It doesn't track how often something recurs, nothing in it expires, and it can't target anything finer than a directory.

**Anthropic's memory tool goes all in on files.** The model gets six commands (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`) under a `/memories` prefix, and your application decides where the files actually live. There are no embeddings and no schema. That makes it very portable and completely unstructured: two agents writing to the same directory have no shared idea of what a file *means*.

**Copilot Memory checks itself against the code.** Every fact carries citations, which are links to specific code locations. Before using a fact, Copilot checks those citations against the current branch. Facts belong to one repository and disappear after 28 days without use. To me, that pairing of *provenance you can check* and *forgetting by default* is the most interesting design in this list. It's also locked inside one product.

**Letta treats memory as context budget.** A block has a `label`, a `value` and a character `limit`, and it's compiled into the system prompt on every step. The format is honest about the cost: memory isn't free, because you pay for it in tokens every turn.

**LangGraph is nearly a key-value store.** Its interface is `put(namespace, key, value)`, where the namespace is a tuple such as `("memories", user_id)`. Its TTL can reset whenever an item is read. Of everything here, it's the closest relative of LoreKit's shape.

**The graphs model the world, not the work.** The MCP reference server keeps entities, relations and observations in a single `memory.jsonl` file. Graphiti stores four timestamps on every edge (`valid_at`, `invalid_at`, `created_at`, `expired_at`), so it can answer "what was true in March?". Both are built for facts *about things*: people, companies, and how a newer fact replaces an older one.

### And yes, people are already proposing standards

I'm not the first to notice this. MacPaw Research has proposed **Portable Memory**, a `.mem` bundle with byte-reproducible serialization, deletion tombstones and optional signing. Its own authors say it's not yet widely adopted. The **Open Memory Protocol** is an April 2026 draft for moving conversations and the memories derived from them between platforms, as a ZIP file with a manifest. Cognee offers a **COGX** exchange format with importers from Mem0, Letta and Zep.

These are worth reading. They have one thing in common: they solve **export**. They answer "how do I move my memory from vendor A to vendor B?" That's a real problem, mostly for personal assistants. The problem I care about is slightly different: **live addressing**. When a CI job, an editor agent and a review bot all work in the same repo at the same moment, how do they write to, and read from, the *same* place? A bundle format doesn't answer that, and an address format doesn't replace a bundle. The two could fit together.

## What they quietly agree on

Strip away the branding and almost every format answers the same four questions, just in different ways:

1. **Where is this true?** A path, a repo, a user ID, a namespace tuple, an entity.
2. **What is its identity?** Something that decides whether a second write is an *update* or a *duplicate*.
3. **What does it say?** Almost always plain text, or JSON when a program is the reader.
4. **When does it stop being true?** Often skipped. When it isn't, the answers range from "28 days unused" to "two full timelines".

They also split on a fifth question: **who writes?** In instruction files it's a person. In the memory tool, Letta and LoreKit, the model writes directly. In Mem0 and Graphiti, a service extracts facts from the conversation. That's a real fork. Extraction gives you memory without asking the agent to do anything. In exchange, it costs a model call on every write and produces a store whose contents you can't fully predict.

They disagree on the **body** too: free text, a capped block, a JSON dict, or a triple. That matters less than it looks, as the CI section below shows.

## Why LoreKit's record looks the way it does

I've written up [every column of the data model](/blog/agent-memory-data-model) before, so I won't repeat that here. What's more useful is to go through the four questions and show where LoreKit borrowed from the formats above, where it went another way, and where I'm not sure it got it right.

### "Where" is a grammar, not a value

```text
global
project::{name}
repo::{owner}/{repo}
branch::{owner}/{repo}::{branch}
```

LangGraph's tuple and LoreKit's scope do the same job. The difference is that a scope is a **string you can write down anywhere**: a URL, a filename, a CLI flag, a YAML key, a log line. It has fixed levels and a fixed read order, with the most specific level read first. The separator is `::` because `/` already appears inside repo and branch names, and git doesn't allow `:` in a branch name, so `::` can't be confused with either. A tuple only means something inside one language's runtime. A grammar means the same thing to a Deno edge function, a Node CLI and `grep`.

It's coarser than a file path and finer than "one repo", which is where coding lessons tend to live. "This branch's spike found X" and "this whole project uses Y" are both easy to express.

It's also clearly shaped by GitHub. `repo::` accepts exactly `owner/repo`, so a GitLab subgroup path like `group/subgroup/repo` doesn't fit today. A standard couldn't keep that.

### "Identity" is `scope` + `key`, and a rewrite is counted

Writing the same `scope` + `key` again updates the existing row and increments `seen_count`. Compare that with an append-only log: if you re-learn something five times, the log holds five near-duplicates, while LoreKit holds one row that knows it was learned five times. A deterministic store gets this salience signal for free, without any model.

To be precise about what it measures: `seen_count` tells you how often something came up. It doesn't tell you whether it's true. A wrong lesson that's re-learned five times is still wrong, just louder. That's why the next two choices exist.

Copilot gets *trust* from citations. LoreKit gets a weaker version of that from provenance: `origin_repo`, `origin_branch`, `origin_commit` and `origin_pr` record where a lesson was learned, but nothing re-checks the code before the lesson is used. If I were starting a standard from scratch, a citation field that readers *may* verify is the first thing I'd borrow from Copilot.

### "What it says" is plain text, and only advisory

The `value` is text, capped at 64 KiB. When LoreKit puts lessons into an agent's context, it labels them *"considerations, not rules."* That's a deliberate line between lore and instruction files. `AGENTS.md` holds what a person has decided. Lore holds what an agent has *noticed*, and it should be easy to ignore when it's wrong. Mix the two in one file and instruction files turn into an unreviewed pile of half-truths.

### "When it stops being true" is opt-in, and that's open to debate

A write can carry `ttl_days`, which sets `expires_at`. Every later write that also carries a TTL restarts the countdown. A write *without* one leaves the existing expiry alone. A lesson written without any TTL never expires, unless a repo or user config sets a default for its scope.

So LoreKit is **permanent by default, with forgetting as an opt-in**. Copilot is the opposite: it forgets by default, after 28 days unused. LangGraph sits in between, with an optional TTL that resets when the item is *read*. LoreKit deliberately never lets a read change a record, so only a write can extend a lesson's life. Old lessons are handled by grooming instead: a review pass that suggests merges, expiries and archives before anything changes.

I go back and forth on which default is right. Forgetting by default keeps a store honest without anyone tending it. Permanent by default means you don't lose the hard-won lesson about the bug that only shows up once a quarter. A shared format should probably let both exist and make the choice visible on each record, rather than settle it once for everyone.

What LoreKit doesn't do at all is keep Graphiti's two timelines. A coding lesson like "the integration tests need Postgres up first" is rarely a historical fact you'd want to look up as of a past date. It's either still useful or it isn't. I'm not sure that holds forever, and it's one of the open questions at the end.

### "What kind" is a short, closed list

`kind` is one of `lesson`, `bus` or `signal`, and `host` names the loop that wrote the record. Each kind is read on a different schedule. A `lesson` is read every run. A `bus` record is a transient outcome, read only when deciding what to promote to a permanent rule. A `signal` is a durable filter for one repo. The list is closed on purpose, so adding a kind means changing the schema. None of the other formats makes this split, and without it, a store fills up with records that push each other out of the context window.

### On disk, it's a file you can `cat`

In the offline store, each record is one Markdown file per `scope` + `key`, and its frontmatter mirrors the columns of the hosted database row. Here's one, trimmed (the real file also lists the empty provenance fields as `null`):

```markdown
---
scope: "repo::acme/checkout"
key: "tests-need-local-postgres"
tags: ["ci","gotcha"]
created: "2026-10-02T09:14:00.000Z"
updated: "2026-11-04T16:41:12.000Z"
origin_commit: "0f4a1c9"
expires_at: "2026-12-04T16:41:12.000Z"
seen_count: 4
kind: null
host: null
---
Integration tests need Postgres up first: docker compose up -d db.
```

Every value in the frontmatter is JSON-encoded. JSON is a strict subset of YAML, so the file is still valid YAML, still easy to grep, and LoreKit reads it with a few lines of code and no YAML library.

When it reads a file, LoreKit is tolerant: a field missing from an old file counts as absent, which is why files written before `seen_count` existed still load. But it isn't yet *lossless*. Rewriting a record keeps only the fields LoreKit knows about, so a field some other tool added would be dropped. That's exactly the kind of gap a shared format has to close: **preserve what you don't understand**.

The shape is also close enough to a memory-tool file or an `AGENTS.md` that these formats could meet halfway. The frontmatter would carry the address and the lifecycle, and the Markdown body would carry the note.

## The test: memory no model wrote

This part came from somewhere I didn't plan, and it's the part I find most convincing.

CI jobs need memory too. A test workflow wants to know which tests were flaky last time. A deploy job wants the last SHA it shipped. A review bot wants to know what it already commented on. None of that involves a model. The usual answers are `actions/cache`, or an artifact bucket nobody else reads.

LoreKit stores this in the **same record**. The only difference is the body: a versioned JSON envelope instead of prose.

```json
{
  "v": 1,
  "updated_by_run": "https://github.com/acme/checkout/actions/runs/123456789",
  "commit": "0f4a1c9",
  "data": {
    "flaky": ["src/queue.test.ts::retries on 429"],
    "consecutive_green": 3
  }
}
```

The job writes it with the CLI, piped straight from `jq`:

```bash
RUN_URL="${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}"

jq -nc --arg run "$RUN_URL" --arg sha "$GITHUB_SHA" --argjson data "$NEW_DATA" \
  '{v: 1, updated_by_run: $run, commit: $sha, data: $data}' \
| npx @lorekit/cli write \
    --scope "repo::${GITHUB_REPOSITORY}" --key 'ci-state::flaky-tests' \
    --tags 'ci::test-state' --kind bus --host ci \
    --ttl-days 7 --remote --json
```

Every concept from the lesson record carries over, with no new fields:

- **Scope works the same way.** State for the main branch lives at `repo::`. State for a single PR lives at `branch::`, so it goes away when the branch does.
- **Identity works the same way, with a stricter rule: one key per fact, overwritten in place, never one key per run.** Because the same `scope` + `key` is an update, a job that runs a thousand times still holds one row. A key per run ID would turn a memory store into a slow artifact bucket.
- **`kind` keeps the record out of an agent's way.** A record with `kind: bus` is left out of the lessons an agent is shown at the start of a session, so a JSON blob never competes with real lessons for context.
- **The TTL becomes a liveness check.** The job passes `--ttl-days 7` on every run, so every run restarts the countdown. The expiry then measures how long the job has been *silent*, not how old the record is. The state lasts as long as the job keeps running, and disappears a week after someone deletes the workflow. A stale flaky-test list is worse than none, so this is the right failure mode.
- **The body carries its own version.** Checking `v` is the reader's job. A reader that sees a version it doesn't know falls back to its first-run behaviour instead of guessing.

The payoff, and the reason to do this instead of `actions/cache`, is that **the agent and the job read the same store**. CI writes `ci-state::flaky-tests`. An agent asked to "fix the flaky tests" reads that exact key in the same repo scope and starts from the real list. The agent's findings go back as a *lesson* right next to it. The state record says what's true right now, and the lesson says what was learned about it. These are two kinds of record in one shape, with no import step between them.

That's why I think it's a good test for an open format. A shape that only fits prose written by a model is a chat feature. A shape that also holds JSON written by a shell script, with the same address, identity and lifecycle, is infrastructure. (The [full CI recipe](/docs/use-cases) covers tokens, guardrails, and why the store must never sit on a build's critical path.)

## What a skeptic would say

These are the objections I'd raise if someone else had written this post, with my best answer to each.

**"This is just your product's schema dressed up as a standard."** That's fair, and it's why I've tried to separate the core from LoreKit's extras below. LoreKit's job is to show that a shape like this holds up in daily use. It's not a claim that the shape should win. If an existing proposal adopted a scope grammar and the four core fields, I'd happily move LoreKit onto it.

**"MCP is already the standard."** MCP standardises the *call*, not the *record*. Two memory servers that both speak MCP can expose completely different tools, with different arguments and different meanings: the reference server's `create_entities`, LoreKit's `memory.write`, and dozens of others. The agent can call any of them, but no two of them agree on what a memory is.

**"Just use files in git."** For one person and one tool, I mostly agree, and LoreKit's offline store *is* files. What plain files don't give you is agreement on what a file *means*: what it applies to, whether it repeats an earlier lesson, and when it stops being true. Frontmatter is where that agreement would live.

**"Shared memory is a prompt-injection channel."** Yes. Anything an agent reads can steer it, and a shared store widens who gets to write those things. LoreKit's partial defences are:

- lore is labeled advisory
- every record carries provenance, so you can see where it came from
- tokens can be write-only or read-only, so a CI job's write-only token can't read the team's lore back out

None of that makes poisoning impossible. A standard would need a trust story, and citations plus signing (which Portable Memory already proposes) are the obvious starting points.

**"Without embeddings, you'll miss everything that's phrased differently."** Sometimes, yes. The [data-model post](/blog/agent-memory-data-model) makes the case for structure first. The point here is narrower: a shared format shouldn't *require* vectors. An index is something a reader can build on top of the records, not something stored in them.

**"Another standard won't fix fragmentation."** That's the xkcd 927 objection: try to unify everything and you end up with one more competing standard. It's the strongest one. The honest answer is that I'd rather add an **address and lifecycle** to formats that already exist than create a new container. That's a smaller ask, and a scope string fits in a frontmatter field, a JSON key, or an `.omp` memory record equally well.

## What an open format might need

Here's my current guess at the smallest useful core, written down so people can argue with it:

- **An address grammar.** A string with defined levels and a defined read order. Not a file path, and not a tuple tied to one language. It should handle more than GitHub's `owner/repo`.
- **An identity rule.** Address plus key is unique, and a rewrite updates the record and is *counted*.
- **A body.** Text by default. JSON is allowed when the reader is a program, with the version stamped inside the body.
- **A lifecycle.** Created and updated times, an optional expiry with an explicit rule for what extends it, and soft deletion.
- **Provenance.** Where a record was learned, ideally with citations a reader *may* verify.
- **A kind.** Enough to tell a lesson from an event from a filter, so readers can budget for each.
- **Lossless round-trips.** Readers keep fields they don't understand when they rewrite a record. LoreKit doesn't do this yet.

Everything else should stay free to vary: the storage engine, the ranking, whether you add embeddings on top, and whether an extractor or the agent does the writing. OpenTelemetry succeeded because it standardised the data model and the wire format, not anyone's backend. I work with it every day at [Dash0](https://www.dash0.com), and I've seen how much one shared shape makes possible.

And the questions I honestly can't answer yet:

- **Are four scope levels right?** Monorepos want a level between `repo` and `branch`. Organisations want one above `project`.
- **Should forgetting be the default?** Copilot says yes, LoreKit says no, and LangGraph extends a record's life whenever it's read. Which of those should a shared format assume?
- **Do coding lessons need two timelines?** Graphiti's argument is strong for facts about the world. Is there a coding case where "what was true in March" matters?
- **Should citations be part of the core?** Copilot's check-before-use is the best defence against stale memory I've seen, but it ties a record to a code host.

The schema, the scope validator and the on-disk format are all open in the repo. If you build one of the formats in the table above, I'd especially like to hear where this shape breaks for you.

## See the files for yourself

The quickest way to judge whether this shape is any good is to look at the files it writes:

```bash
npx @lorekit/cli install
```

That gives you a folder of plain Markdown records you can open, grep and diff. Then tell me what's missing.
