# Key decisions (do not relitigate)

Full rationale for the architectural decisions summarised in the root
[`CLAUDE.md`](../CLAUDE.md) → **Key decisions** index. Each decision here is the
canonical, verbatim record; the CLAUDE.md entry is a one-line headline that links
back to the matching section below. **Do not relitigate these** — read the
rationale before proposing a change that reverses one.

---

## Dashboard is a CLIENT of LoreKit's REST API

**The dashboard is a CLIENT of LoreKit's REST API — it does not query PostgREST for memories.** `packages/web`'s memory reads and writes go through the `memories` edge function (`packages/web/src/lib/api/`), authenticated with the signed-in user's own Supabase JWT (`resolveRestAuth`'s third tier), typed end-to-end by `@lorekit/schemas`. The dashboard previously reached past its own API and queried the table with supabase-js, which meant a SECOND hand-written copy of every predicate the handlers already own — tenant scope, the active-vs-archived partition, the expiry filter, the keyset cursor, the label-containment array quoting. Two implementations of one contract drift, and these had: the row-cap bug `GET /memories/scopes` was created to fix (00039) was still live in the dashboard's scope tree, its label catalog and its Overview charts long after the endpoint shipped, and the Overview additionally UNDERSTATED every scope's total (a `limit 1000` over a `created_at desc` ordering drops the oldest rows of every scope). **The rule that follows is the point of the change: a capability the dashboard needs becomes part of the PUBLIC contract** — schema in `@lorekit/schemas`, handler, OpenAPI registration, `migrations.test.sql` assertions — rather than a private query. That is what `GET /memories/tags` (00050) and `GET /memories/activity` (00051) are, and why `GET /memories` grew `q` / `created_since` / `created_until` / `tags_mode` / `sort` instead of the Explorer keeping its own query: every one of those filters is now available to the CLI and to agents too. Aggregates stay in Postgres for the 00039 reason — a `select … limit N` plus a browser-side reduce is silently wrong for exactly the accounts with the most data. **A filter value is encoded ONE way**: `likeNeedle` escapes the LIKE metacharacters and `quoteFilterValue`/`ilikeClause` double-quote the result, the only mechanism PostgREST's URL grammar defines for a reserved character inside a logic tree — percent-encoding cannot work, because `.or()` appends through `URLSearchParams` and the `%` is re-encoded, so `%2C` arrives as literal text. `GET /memories?q=` and the `filter` tree of `POST /memories/search` share that composition, and both filters are exercised against a live stack in `memories-api.integration.spec.ts` → "list filters" (the Storybook MSW handler reimplements them, so it proves nothing about the handler). **Supabase-js is NOT banished**: it remains the auth client (sign-in, session, password) and still backs the server actions for surfaces the REST API does not expose (orgs, invites, API tokens, audit log, scope bindings, GitHub installations) — those are the follow-up, not a licence to add a new direct `memories` query. **The rule generalises to EVERY new data surface, not just memories, and it is a hard requirement** (`packages/web/CLAUDE.md` → "Data access goes through a REST endpoint"): a new capability gets a schema in `@lorekit/schemas` (+ `./<name>` export + `MIRRORED_SCHEMA_FILES` entry), a handler in a `supabase/functions/<fn>/`, an OpenAPI path, and `migrations.test.sql` assertions — never a fresh supabase-js `.from(…)`/`.rpc(…)` in a component. **The blog like counter is the worked example and the one PUBLIC (unauthenticated) endpoint**: the `blog` edge function (`GET`/`POST /blog/likes`, migration 00055 `blog_post_likes` + the anon-granted `lorekit_blog_like` RPC, `migrations.test.sql` §73) is consumed via `packages/web/src/lib/api/blog-likes.ts` — the only difference from the other routes is that it sends no token (`publicRestFetch`), because the blog is public and its likes are anonymous. It does NOT use `resolveRestAuth`/`createRouter` (no user, no tenant, no per-user usage event); it has its own two-line dispatch and a service-role client, safe only because the sole operations are read/increment of one global counter (see `supabase/functions/blog/CLAUDE.md`). Do not collapse it back into a direct RPC call.

## MCP server endpoint is a static production URL

**The MCP server endpoint is a static production URL — never write a `<ref>` placeholder in user-facing content.** The hosted MCP server lives at a fixed Supabase project ref (`pqokxlhvnosogizsjztg`), so any URL an end user sees — Getting started / Learn pages, `.lorekit.json` / config examples, dashboard copy, docs — MUST use the concrete `https://pqokxlhvnosogizsjztg.supabase.co/functions/v1/mcp` (the same literal `GettingStartedContent.tsx`'s `MCP_URL` uses), NOT `https://<ref>.supabase.co/...` or `<project-ref>`. A placeholder is only acceptable in migration/deploy tooling that legitimately targets multiple projects (e.g. the `resolveProjectConnection` `<project-ref>` guard, which *rejects* an unconfigured placeholder). See the Endpoints table.

## Lore Explorer filters through ONE two-level command menu

**The Lore Explorer filters through ONE two-level command menu and a row of pills — never one picker per dimension, and never a client-side narrowing.** The Explorer filtered on labels alone, behind a bespoke popover (`LabelFilter`). It now filters on nine dimensions — label, kind, host, owner, agent, trigger, repo, branch, pull request — and the shape that scales is Linear's: a single **Filter** trigger opening a menu whose first level is the DIMENSION list and whose second is that dimension's values, with committed conditions rendered below as three-segment pills. A picker per dimension would put nine controls in a row that has to survive a phone and would still not answer "what else can I filter by?"; here a new dimension costs one row in `FILTER_FIELDS` and nothing else. **Semantics are OR within a dimension, AND across dimensions**, because that is the only combination a flat pill row can render without inventing a precedence grammar — cross-dimension OR and nested groups stay in `POST /memories/search`'s `filter` tree, which already expresses them. **Every dimension is filtered SERVER-side** (`GET /memories` gained `source_agent` / `trigger` / `origin_repo` / `origin_branch` / `origin_pr` plus a `*_mode` of `in`/`nin`, `tags_mode` gained `none`, and `owner` — value `personal` or an org slug — landed in 00064), never by narrowing the loaded pages: those are keyset pages, so a client-side narrowing of a filter the user can actually type is "no matches" on page one and matches on page three. **Owner was the last exception** — a separate client-side `OwnershipFilterBar` over the loaded pages — and 00064 folded it into the same machinery as a real facet dimension: `lorekit_memory_facets`, `lorekit_memory_activity` and `GET /memories` all resolve `personal` → `org_id is null` and an org slug → the caller's member org (slugs resolve against member orgs only, which the visibility predicate already guarantees), so the owner filter agrees with the list, the drill-down counts and the stat header like every other dimension. The `?owner=` deep link the accept-invite flow used is superseded: it is still READ (a `'personal'` value → an `owner` filter; `'all'` / the legacy `{orgId}` form → none) but never written, and the flow now deep-links a slug-keyed `owner` filter directly. **The value catalog is its own query, never derived from the loaded pages** (`GET /memories/facets`, 00052) for `useTagCatalog`'s reason, which only sharpens with more dimensions — derived from the loaded pages the options would shrink to whatever the current page returned, and the cross-dimension type-ahead could only ever surface values already visible in the list, which is exactly when you did not need it. The ENDPOINT is no longer filter-INDEPENDENT: **00057 made the counts drill-down** — it takes the caller's active filters and counts each dimension with every OTHER one applied but not its own (self-exclusion), so a value's count is what selecting it would yield while the dimension you are standing in still shows everything you could switch to. Unfiltered, it returns 00052's global catalog unchanged; the Explorer now passes its active filter bar and the selected scope (`listFacetsPostRequest` ← `filtersToFacetBody` + `useFacetCatalog`'s `scope`, keyed on both — `listFacetsRequest` ← `filtersToFacetParams` is the equivalent GET form, kept and spec-covered but no longer called from this package), so its menu counts drill down as you build the bar and match the scoped list. `kind`/`host`/`owner` have `FILTER_FIELDS` rows now, so all nine dimensions are filterable — `FacetName` and `FilterField` are one-to-one, and `filters.spec.ts` executes that against `MemoryFacetSchema` so a facet added server-side without a pill fails a test instead of being silently dropped. The one residual widen/switch loss is that a value counting zero under the other filters emits no row, so it drops out of the menu until the filter is cleared. The counts also do NOT mirror `q` / `key` / `created_since` / `created_until` — with a search or date window active they are upper bounds, not exact yields, because mirroring `q` would mean a second implementation of `likeNeedle`'s escaping in plpgsql. **Selection is URL-backed** (`?filters=`), so a filtered view is a link; the pre-existing `?tags=` param is still READ (never written) and translated by `filtersFromLegacyTags` into a `label` filter with the `all` operator, which is what it has always meant — links in PRs, Slack and `lorekit link` output keep resolving to the filter they name. The decision logic is pure and node-tested in `lib/filters.ts`; `FilterMenu`/`FilterPill` are the shell. **Do not re-add a per-dimension trigger, a client-side dimension filter, or a second catalog query.** **The Explorer reads those server-side filters over a JSON BODY** (`POST /memories/list` / `/facets` / `/activity`), not a query string: a query string caps each dimension at 2048 characters (`ValueListSchema`), so the number of values a dimension can hold depended on how long the values happened to be — with realistic ~28-character host names the Explorer stopped loading somewhere between 50 and 75 selected values and rendered only "Failed to load memories. Please refresh." — and even under that cap eight dimensions compose a URL past what the gateway accepts, which fails with no LoreKit error envelope at all. Raising the cap only moves the first wall and makes the second arrive first, so this is a transport change rather than a bigger number. **The GET forms stay fully supported and unchanged** (the CLI, MCP and API-token callers use them, and a link carrying a few filters is better as a URL); the two transports cannot drift because neither handler decides anything — `dimensionsFromQuery` and `dimensionsFromBody` (`@lorekit/schemas/dimensions`) both produce ONE `MemoryDimensions` and a single predicate function turns that into SQL, so a dimension is one field and one line rather than two of each. Body dimensions are arrays bounded at 1000 values × 512 characters — an explicit limit rather than an emergent one — and both forms report under the SAME `usage_events.tool_name`, because splitting `memory.list` in two would have read as an outage on the day the dashboard switched.

## Mobile transient selection surfaces use the BottomSheet primitive

**On mobile, transient selection surfaces use the `BottomSheet` primitive — never an anchored popover.** Any popover / menu / picker / combobox that opens over the page on the phone breakpoint (the `md:hidden` layout) MUST render its body in `components/ui/BottomSheet.tsx` (blurred backdrop, drag-to-close, background `inert`, focus + body-scroll-lock), not the desktop anchored popover — a popover assumes a mouse and a precise click-outside and can overflow a narrow screen, whereas a bottom sheet is the platform-native shape (thumb-reachable, dismissed by tap-backdrop / drag-down / Escape). Keep the anchored popover for `md`+ and branch on a `variant` (or breakpoint), sharing ONE body between the two containers so they cannot drift — `FilterMenu` is the reference (it replaced `LabelFilter`, which held this role before): it renders a single `panel` into either the desktop popover or the `BottomSheet`. New pickers follow this split rather than shipping a popover-only control. **Form-heavy panels with a pinned footer** — the memory editor `LessonDetailSheet`, whose save/discard + archive bar must stay pinned below a scrolling body, which the single-scroll `BottomSheet` body can't host — adopt the sheet *geometry* directly (bottom-anchored, rounded top, drag handle, drag-to-close via the same pure `shouldDismissSheet`) instead of nesting inside the component, while keeping the right-side drawer at `md`+. The presentation is chosen by `useIsMobile()` (`lib/hooks/useMediaQuery.ts`) because Motion `initial`/`animate` variants can't switch on a Tailwind breakpoint. That hook is JS (`matchMedia`, re-renders only on a breakpoint cross, never on resize) and backed by a **single shared listener per query** via `useSyncExternalStore` + a module-level registry — N components watching the same breakpoint cost one listener, not N — with `MOBILE_QUERY` as the single source of truth so every consumer shares the same entry.

## Write-only tokens (lk_wo_*)

Write-only tokens (`lk_wo_*`) store `permissions: ['write']` in the existing `text[]` column — zero migration. Prefix derivation and tool gating (`READ_TOOLS`/`WRITE_TOOLS`/`toolRequires`/`tokenPrefixFor`) are consolidated into a shared pure module (`packages/mcp-core/src/permissions.ts`), mirrored self-contained into the edge function and lightly into web — the same reasoning as `limits.ts`/`webhook-secret-select.ts`: the edge function has no test harness, so the pure module is the only unit-testable home for gating logic. The Node.js `mcp-server` gets no gating — it has no API-token auth path at all, and adding one is out of scope.

## API token scoping (scopes + orgs)

**API token scoping** (`supabase/migrations/00068_api_token_scoping.sql`) adds two axes to a `lk_*` key on top of the read/write one the prefix already encodes: an allowlist of scope patterns (`api_tokens.scopes`) and a tenancy (`org_access` ∈ `all` | `personal` | `selected`, with `org_ids`). **00068 is the data model plus the two predicates only — 00068 alone enforces nothing.** It is no longer the whole story: `00069_api_token_scoping_enforcement.sql` makes the predicates binding in the transports (`mcp/auth.ts`, `_shared/api/auth.ts`, `mcp-handler.ts`, `applyTenantScope` / `applyRestTenantScope`) and inside the SQL functions the transports cannot stand in front of (see the enforcement decision below), the dashboard's `TokenManager.tsx` sets the columns, and `00070_audit_log_api_key_scope_change.sql` audits every change. The decisions below describe the model; the enforcement decision describes the behaviour that is live. Five decisions, none of them to be relitigated:

1. **EMPTY MEANS UNRESTRICTED.** `scopes = {}` is "every scope the owner can see", not "none". Empty-means-deny reads safer but bricks every existing key on deploy AND the key the dashboard auto-generates on first login (`onboarding-steps.tsx`), which has no UI to pick scopes from. Restriction is opt-in and additive; the column defaults reproduce today's behaviour exactly.
2. **TENANCY IS A TRI-STATE, NOT A LIST.** A bare `org_ids uuid[]` cannot say "personal only" — an empty list would have to mean both "unrestricted" and "no orgs", the two most different answers in the space. Hence the enum, with the list meaningful (and permitted) only under `selected`. A personal row is reachable under every tenancy: `personal` narrows which ORGS are reachable, it never revokes the owner's own memories.
3. **PATTERNS REUSE THE EXISTING WILDCARD GRAMMAR.** `repo::mthines/*` is already what users type (`expandScopeForSearch`), so the allowlist takes the same shape rather than inventing a second matcher — down to the same `[a-z0-9._:/-]` charset, because an allowlisted pattern lands in the same kind of PostgREST predicate as a searched one, and the same `\_` LIKE escape, so `repo::my_org/*` stays owner-exact, and the same WILDCARD POSITION: a trailing `*` counts only directly after a `/` or a `::`. Interior wildcards (`repo::*/lorekit`) are not supported, and neither is a trailing star off a segment boundary (`repo::mthines/lore*`) — under an "any trailing star" rule that pattern would allowlist `repo::mthines/lorekit-private` while being refused as a search filter, i.e. two grammars wearing one syntax. A restricted key fails CLOSED on a scopeless operation (`memory.purge_expired`, the account-wide reads); an unrestricted one is unaffected.
4. **THE KEY WINS OVER A SCOPE→ORG BINDING.** [Binding](#scopeorg-binding) auto-routes a write under a bound scope into that org. A key restricted to `personal` writing under a bound scope must NOT land in an org it was never granted — the binding is a convenience, the key restriction is an authorization boundary, and a boundary a convenience can widen is not one. The write falls back to personal, exactly as a non-member's write already does.
5. **WRITES GO THROUGH AN RPC, NOT AN UPDATE POLICY.** 00002 deliberately gave `api_tokens` no UPDATE policy. Adding one now would put "may this actor point this key at this org?" in a `WITH CHECK` expression that cannot consult `org_members` without re-deriving the tenancy predicate a second time. `lorekit_api_token_set_scoping` is the Phase-3 shape instead: SECURITY DEFINER, actor from `auth.uid()`, org ids validated against the actor's own membership so the row can never record access that does not exist.

**Enforcement (00069) lives in exactly three LAYERS, and refusal-vs-narrowing is decided by whether the request NAMED a scope.** (1) The transport dispatchers — `mcp-handler.ts` and the REST handlers via `firstDeniedScope` — refuse a named scope outside the allowlist, because an empty page reads as "there is nothing there" and sends the caller hunting a data bug; the same layer refuses an account-wide sweep outright, from the one `account-wide-tools.ts` module both surfaces import. (2) The query narrowing: `applyTenantScope` (and its REST twin `applyRestTenantScope`) for every read that names no scope, which a per-call-site check structurally cannot cover, and `applyKeyScopeFilter` for the personal-only write family (`PATCH`, `DELETE`, restore), which deliberately does not widen to org rows and so needs the allowlist half on its own. `tenant-scope-usage.spec.ts` fails a handler in either family that drops it. (3) The SQL functions the transports cannot stand in front of — the two mutation gates `memory_write` and `memory_delete`, and the five per-scope aggregates `lorekit_memory_scopes`, `lorekit_memory_activity`, `lorekit_read_activity`, `lorekit_memory_tags` and `lorekit_memory_facets` — take the restriction as defaulted parameters, because the edge runs on the service-role client, so every check above them is advisory, and because the scope→org binding is only visible inside the RPC. Passing the restriction from the caller is safe for the same reason `p_user_id` is (00046): only the edge reaches these functions with one attached, on a verified service-role connection, having read it out of `api_tokens` by token hash microseconds earlier, and the widest forgeable value is the default, so a forged value can only deny the forger. The edge mirror of `tenant-scope.ts` moved from `mcp/` to `_shared/` in the same change: the REST surface needed the same arithmetic, and two edge copies of one authorization predicate is the drift the mirror exists to prevent.

The two request-time predicates (`lorekit_api_token_scope_allowed`, `lorekit_api_token_org_allowed`) live in SQL because the write path's last unbypassable gate is inside `memory_write`, which cannot call TypeScript; `@lorekit/schemas/api-key.ts` carries the TypeScript twins for the transports, and `api-key.spec.ts` + `migrations.test.sql` §81 pin the cases that would let them drift. §81 is also the FIRST DB-level assertion this repo has ever had about `api_tokens`.

## Browser RUM init + identity at INIT

**Browser RUM initialises in `lib/dash0-rum.ts`, and identity is set at INIT — never only after login.** `instrumentation-client.ts` is the earliest browser entry point and calls `initDash0Rum()` there so early page-load spans are captured; `Dash0Provider` calls the same idempotent initialiser and owns the one thing that needs the React tree: keeping `user.id` in step with the session (upgrading the anonymous id to the authenticated user id, and dropping back to the anonymous id when the authenticated tree unmounts on sign-out). It does NOT set `page.url.path` — the SDK derives that from `window.location.href` on every signal it emits (`addCommonAttributes` → `addUrlAttributes`), so an app-side copy is only a duplicate second entry. The provider is mounted in the ROOT layout with no `userId` so public pages — marketing, `/docs`, `/login` — are instrumented too, and a SECOND time in the dashboard layout WITH `user.id`; mounting twice is safe because the guard is now one module-level flag rather than a copy per module (it previously was not, and the SDK really was initialised twice per dashboard page load). **Every event carries a `user.id`**: an `anon:<uuid>` from `localStorage` until the visitor signs in. Identifying only on login left 731 of 1108 events and 29 of 36 sessions with an EMPTY `user.id`, which Dash0 folds into ONE indistinguishable anonymous user — anonymous visitors could not be told apart, and a returning visitor could not be told from a first-time one (`session.id` resets per session, so it cannot stand in for a visitor). Do not "simplify" this back to a login-only `identify()`.

## OTEL_SERVICE_NAME must never decide a component's name

**`OTEL_SERVICE_NAME` must never decide a component's name.** `@vercel/otel` resolves `OTEL_SERVICE_NAME || serviceName || 'app'`, so the env var outranks the code, and the OTel env resource detector applies it again independently — there is no config-side way to win. A project-wide value (the documented way to name the Node MCP server) silently renamed the Next.js server runtime to `lorekit`, reporting 326 spans in a 6h window under the `service.namespace` value and splitting the app into two service-map nodes while the browser half correctly said `web`. `register()` now overwrites the variable with the code-declared name and `console.warn`s the conflict. Same reasoning as the edge functions' "do not reintroduce a per-function `SERVICE_NAME` secret".

## VERCEL_ENV must never decide the deployment environment alone

**`VERCEL_ENV` must never decide `deployment.environment.name` on its own — it is always cross-checked against `NODE_ENV`.** `VERCEL_ENV` is a *value*, not a proof of where the process runs: `vercel env pull` writes the selected environment's variables — `VERCEL_ENV=production` included — straight into a local `.env.local`, and `next dev` loads that file like any other. From that moment a laptop stamps every span and RUM event `deployment.environment.name=production`. That is not hypothetical: a local Turbopack dev server's `ENOENT … .next/server/app/(auth)/login/page/app-build-manifest.json` failures pushed the production `web` SERVER error ratio to 12 % and fired the "Web — high backend error rate" check rule while the deployed site was healthy — every failing resource also carried `node.env=development` and a `/Users/…` path. The rule that follows is the point: **an attribute describing WHERE a process runs must be derived from something the process cannot be handed in a file.** `NODE_ENV` is that thing — every Vercel production and preview deployment serves a `next build` output with `NODE_ENV=production`, while `next dev` and `vercel dev` always run with `NODE_ENV=development` — so a non-production `NODE_ENV` is conclusive evidence of a dev server and a claimed `production` / `preview` is clamped away to `local`, with a one-time `console.warn` naming the value that was dropped. A claimed `development` is NOT clamped — `vercel dev` genuinely is that environment, so it is reported as `development` and nothing is warned; since `vercel env pull` writes Development by default, that silent path is the common one, and it is why the fix is to clear `VERCEL_ENV` out of `.env.local` rather than to rely on the warning. Both emitters resolve through ONE shared pure module (`packages/web/src/lib/otel-deployment-env.ts`; server `src/instrumentation.ts`, browser `src/lib/dash0-rum.ts`) so the two halves cannot drift, and an unrecognised `VERCEL_ENV` falls back to `local` rather than being passed through, so a typo can never invent a new environment. **`VERCEL` is deliberately NOT also checked** — `vercel env pull` writes the system variables too, `VERCEL=1` among them, so the same `.env.local` that supplies the bad `VERCEL_ENV` supplies a matching `VERCEL` and the gate closes nothing; it would only add a way for a real deployment to be mis-detected as `local` if that variable ever stopped reaching the Next.js server runtime, which is a silent loss of production telemetry — the worse failure. The accepted residual is a deliberate local `next build && next start` against pulled production env, a rare act, whereas `next dev` is what every contributor runs all day and is what caused the incident. Same shape, and the same reasoning, as "`OTEL_SERVICE_NAME` must never decide a component's name": an env var silently outranking the code and mislabelling a component's telemetry. Do not reduce this to a bare `VERCEL_ENV` read, and do not add the `VERCEL` gate.

## Caller identity belongs on the ROOT request span

**The caller's identity belongs on the ROOT request span, not only on the auth child span.** `resolveRestAuth` records `auth.type` / `auth.user_id` on its `lorekit.rest.auth` CHILD span, which left every REST root span (`lorekit.memories`, `lorekit.orgs`) with no identity and made "group this surface by user" a join. The MCP surface has always set both on its root span (`mcp/index.ts`), so `createRouter`'s dispatch now does the same for REST — one site, covering every current and future route, right beside the usage event that already computes the same two values. It reports `usageAuthType` (`jwt` / `api_key` / `service`) rather than the raw REST `auth.type` (`user` / …) so MCP and REST aggregate as ONE series, the same normalisation rationale as `restToolName`; the child span keeps its raw value so existing queries do not break. **This is what makes web ↔ CLI ↔ MCP correlation possible without device fingerprinting**: all three authenticate as the same LoreKit user and all three land on `api`, so the join key is the account, never an IP or a machine id.

## Edge Function is self-contained Deno (no import map)

Edge Function is self-contained Deno (no cross-package imports) — Node.js MCP SDK incompatible with Deno. **This is enforced, not advisory, as of the import-map removal:** `memories`/`orgs`/`openapi` violated it by importing `@lorekit/schemas/*` and `zod` as BARE specifiers, which resolve only if something hands Deno `supabase/functions/import_map.json`. Nothing did — current Supabase CLI versions dropped auto-discovery of that filename and `setup-cli` pins `version: latest`, so it broke with no commit to blame, and all three died at boot with `Relative import path "@lorekit/schemas/memory" not prefixed with / or ./ or ../`, visible only as an opaque `503 BOOT_ERROR` through the REST passthrough (six CI runs across five branches before the container log was ever captured). Declaring `import_map` per function in `config.toml` was tried and does NOT reach the local `supabase start` runtime. The map is now **deleted**: schemas are mirrored into `supabase/functions/_shared/schemas/` (`node scripts/sync-edge-schemas.mjs`, the `limits.ts` mirror pattern) and `zod` / `@asteasolutions/zod-to-openapi` are written as fully-qualified `npm:` specifiers. Two guards run in the mocked `check` job: `edge-bare-specifier.spec.ts` (no file reachable from a function may use a bare specifier, and no function may reach source outside `supabase/functions/`) and `edge-schema-parity.spec.ts` (the mirror matches `packages/schemas/src` exactly, modulo the `npm:` rewrite). Never add an import map back — the invariant is stronger and cannot be disabled by a CLI upgrade.

## Memory cap enforced by a DB trigger

Memory cap enforced by a DB trigger (not app-side counting) — the write-path `userId` is auth-type-sensitive (null for JWT users, RLS-scoped), so only a `NEW.user_id`-keyed trigger is auth-agnostic and unbypassable.

## Webhook secrets are repo-scoped

Webhook secrets are **repo-scoped**, matched by the delivery's `repository.full_name` against a stored `repo` column (`webhook_secrets.repo`, nullable) — not by joining `repository.owner.login` against `auth.users` (that join is O(all users), capped at 1000, and fails for org-owned repos where the owner login is the org, not any user's personal GitHub login). A null-`repo` row is a legacy/global fallback kept for back-compat; `GITHUB_WEBHOOK_SECRET` remains the last-resort env-var fallback. The selection logic (`selectWebhookSecrets`) is pure and lives in `packages/mcp-core` (vitest-tested, no Deno test harness exists), mirrored self-contained into the edge function — the same pattern as `limits.ts`. Webhook server actions authenticate via the Supabase user JWT + RLS, not an `lk_rw_*` API token — the `lk_rw_*` rule is for MCP `api_key` tool calls, not dashboard server actions.

## Audit logging is captured at the app layer

Audit logging (`audit_log` table, `supabase/migrations/00010_audit_log.sql`) is captured **at the app layer** — an explicit `recordAudit`/`recordAuditEvent` call right after each sensitive mutation succeeds (API-key create/revoke, webhook-secret create/rotate, memory create/update/archive/restore/delete), not by DB triggers on the underlying tables — the app layer can resolve the actor (`auth.uid()` for dashboard actions, the resolved token/user for MCP, `null` for service-role/CI) and shape a human-readable `target`/`metadata` that a trigger on `memories`/`api_tokens`/`webhook_secrets` cannot. **The one deliberate exception is `user_limits`**: no app-layer code path writes that table today (raising a limit is a raw SQL upsert), so there's no call site to instrument — an `AFTER INSERT OR UPDATE OR DELETE` DB trigger (`audit_user_limits()`) is the only way to capture `limit.override` events, mirroring the `enforce_memory_cap()` DB-trigger precedent for the same reason (the write-path actor isn't app-visible there either). `recordAudit`/`recordAuditEvent` never throw — a failed audit write must never break the primary operation it's auditing. Mirrored self-contained into `supabase/functions/_shared/audit.ts` for the Deno edge tree, the same pattern as `limits.ts`/`created-at.ts`. **The REST handlers participate in exactly the same model through that one module.** `audit.ts` was promoted out of `mcp/` into `_shared/` precisely so there is ONE edge audit writer: `memories/handlers/{create,update,remove,restore,purge}.ts` call the same `recordAudit` the MCP tools do, with matching `action`/`resourceType`/`target`/`metadata` shapes so the two surfaces produce comparable rows, after the primary operation succeeded and only when it changed something. Never add a second edge writer (e.g. under `_shared/api/`). **The actor is resolved by `auditUserId` (`_shared/api/auth.ts`, re-exported from the pure `_shared/rest-audit-actor.ts`): the resolved user for BOTH `api_key` and user-JWT callers, `null` ONLY for service-role.** This REVERSES the earlier 'mirror MCP's null-actor limitation, don't fix it here' decision, which was wrong: a JWT caller's db client is `userClient(jwt)` (ANON_KEY + bearer), so RLS applies and `auth.uid()` IS that user's id — `rls_audit_log_insert`'s `with check (user_id = auth.uid())` is therefore SATISFIED by supplying the caller's own id and VIOLATED by `null`. The old behaviour did not produce a 'comparable row'; it produced no row at all, silently, because `recordAudit` never throws. Service-role stays `null` — no human actor, and that client bypasses RLS anyway. **Consequence, stated plainly: REST now attributes JWT callers correctly where MCP (`mcp/auth.ts`'s `getUserId`) still records `null` and still loses those rows. `getUserId` is the side that should converge on the REST rule — never 'restore symmetry' by reverting REST.** **The `orgs` REST handlers ARE now audited** (all 7 mutating routes: `org.create`/`org.rename`/`org.delete`/`member.role_change`/`member.remove`|`member.leave`/`member.invite`/`member.revoke`), which the null-actor rule had made pointless; their `action`/`resourceType`/`target`/`metadata` shapes deliberately match the equivalent `orgs.ts`/`org-invites.ts` dashboard server actions so the two surfaces stay comparable. The structural guard `packages/mcp-core/src/audit-coverage.spec.ts` parses each function's route table, resolves handlers through that index's own imports, and FAILS for any mutating route (unsafe method, not `requires: 'read'`) whose handler has no `recordAudit` call — its `AUDIT_EXEMPT` list is empty and any future exemption must be a visible edit. **The action vocabulary is ONE list**: `packages/schemas/src/audit.ts`'s `AUDIT_ACTIONS` (24 actions), imported by `packages/mcp-core/src/audit.ts` and — via the generated mirror `_shared/schemas/audit.ts` — by `_shared/audit.ts`; `packages/web/src/lib/audit-actions.ts` still re-declares it (web has no `@lorekit/schemas` dep, by design) but `audit-vocabulary.spec.ts` asserts the copy, the web `AUDIT_ACTION_META` keys, and the NEWEST `audit_log` action-CHECK migration (discovered by scanning, never hardcoded) all equal it. That guard exists because the three lists had drifted to 11 / 23 / 24 and `github_app.installation_linked` — emitted by `handleSetupReturn` — was rejected by the CHECK and swallowed on every GitHub App link; `00042_audit_log_github_app_action.sql` widens the CHECK to all 24.

## Usage events recorded once per surface, in the dispatcher

**Usage events are recorded once per surface, in the dispatcher — never per handler.** The MCP side records one `usage_events` row per tool call in `mcp/mcp-handler.ts`; the REST side records one per dispatched route in `_shared/api/router.ts`'s `dispatch`, covering both the returned-response and the thrown-error path. The writer is shared: `recordUsageEvent`/`getUserPlanName` live in `supabase/functions/_shared/usage.ts` and `mcp/limits.ts` re-exports them (that file was always only a *partial* mirror of `packages/mcp-core/src/limits.ts` and is deliberately excluded from `edge-parity.spec.ts`'s whole-file comparison; the parity that exists — `LimitError`, `translateCapError`, the message builders, `checkRateLimit` — is untouched). A REST route reports the **MCP tool name it is the equivalent of** (`POST /memories` → `memory.write`, `DELETE …?force=true` → `memory.delete`, …) so the two surfaces aggregate as one series instead of fragmenting the moment a CLI command moves transports; that mapping is the pure, unit-tested `packages/mcp-core/src/rest-tool-name.ts`, mirrored to `supabase/functions/_shared/rest-tool-name.ts` and drift-guarded by `edge-parity.spec.ts` — never an inline conditional in the router. The REST guard is `auth.type !== 'service'` plus a resolved user; the MCP guard's extra `adapter.supportsHostedBilling` term has no REST counterpart, because the REST functions have no storage adapter and no BYOD mode at all (they always read and write the hosted database), so the flag would be a constant `true`.

## Org/scope sharing is ORG-FIRST (Phase 1)

Org/scope sharing is **ORG-FIRST** (single authoritative shared row owned by an org, not copy-on-share) — Phase 1 (foundations only; full phased arc in `.agent/claude/memory-scope-sharing-ualfuz/plan.md`) ships `orgs`/`org_members` and widens **reads** to org membership; **writes stay personal-only** until Phase 2 (`memory_write` gains no `org_id` parameter this phase). The tenant-visibility predicate lives in exactly ONE enforced place: `lorekit_member_org_ids(uuid)` (`SECURITY DEFINER`, `STABLE`, 00014_orgs.sql), consumed both by the `memories` RLS read policies (00015) and by the mirrored TS helper `applyTenantScope` (`packages/mcp-core/src/tenant-scope.ts` ↔ `supabase/functions/mcp/tenant-scope.ts`, the `limits.ts` mirror pattern) — never a hand-copied `.or()` predicate. `applyTenantScope` is a total function: an empty `orgIds` list returns a personal-only filter and never emits an `org_id.in.()` fragment (that degrades to a PostgREST match-all/error footgun). Two executable drift guards enforce this stays singular: `edge-parity.spec.ts` (mirror parity) and `tenant-scope-usage.spec.ts` (source-scan — every edge read handler must route through `applyTenantScope`, never an inlined `.eq('user_id', ...)`). The uniqueness arbiter partitions org-owned rows (`org_id, scope, key`) separately from personal (`user_id, scope, key` where `org_id is null`) and service-role (`scope, key` where both are null) rows via three mutually-exclusive partial unique indexes (00016) — an org row can never collide with or impersonate the cap-exempt `user_id IS NULL` service partition. `.lorekit/config.json` is (and will remain, per the Phase 4 plan) **advisory only** — membership truth is always the server-side `org_members` table, never a client-committed org pointer.

## Org/scope sharing Phase 2 (org-owned writes)

Org/scope sharing **Phase 2 (org-owned writes)** opens the write path Phase 1 left closed (`.agent/claude/org-sharing-phase-2-writes/plan.md`). `memory_write` gains a trailing `p_org_slug`, but org ownership is **authorization-derived inside the RPC**, never trusted from the caller: it resolves the slug and requires `lorekit_org_can(writer, org_id, 'write')` — the SOLE role→capability source (`supabase/migrations/00017_org_roles_and_author.sql`), covering a new `viewer` role plus `write`/`archive`/`restore`/`hard_delete` capabilities for `member`/`admin`/`owner`. Author attribution is additive `created_by`/`updated_by` columns (org rows keep `user_id NULL`, so a dedicated author pair records the writer without pooling org rows into the writer's personal cap or RLS partition). The memory cap becomes **tenant-keyed**: `enforce_memory_cap()`'s branch order is org → service-exempt → personal (`00018_org_limits.sql`) — the org branch MUST precede the service exemption because an org row always has `user_id IS NULL`, otherwise it would silently inherit the cap-exempt service partition. Destructive ops route through a new role-gated `memory_delete` RPC (`00020_memory_delete_org.sql`) rather than a raw service-role delete/update, because the edge api_key client bypasses RLS and has no other gate available. Rate limiting stays caller-keyed (`lorekit_check_rate_limit(p_user_id, ...)`, unchanged) — a throughput-per-caller guard, distinct from the tenant-keyed storage cap. The read path is untouched: `applyTenantScope`/`lorekit_member_org_ids` remain the sole tenant-visibility predicate (verified by `tenant-scope-usage.spec.ts` + `edge-parity.spec.ts` staying green). The denial signal is a distinct SQLSTATE `LK002` (vs. the cap's `LK001`), translated by `org-permissions.ts` (mirrored edge-parity-guarded, the `limits.ts` pattern) — the capability matrix itself is never duplicated in TS.

## Audit Logs pagination is keyset (cursor), not OFFSET

Audit Logs pagination is **keyset (cursor), not OFFSET** — `listAuditLog` orders `(created_at desc, id desc)` and pages via an opaque `nextCursor` (base64url `{ c, id }`, `packages/web/src/lib/pagination/cursor.ts`). The cursor carries no `user_id`; `listAuditLog` applies its own `.eq('user_id', …)` unconditionally, so a forged/tampered cursor can at worst mis-page the caller's own rows, never widen visibility — that's what makes `decodeCursor` safe to fail closed to `null` (→ first page) without HMAC/signing. Name search (`target ilike '%…%'`) is index-backed by a `pg_trgm` GIN trigram index (`supabase/migrations/00012_audit_log_search.sql`); the keyset seek is covered by `(user_id, created_at desc, id)` (00010's `(user_id, created_at desc)` index lacks the `id` tiebreaker). The pure pagination/filter logic lives in `packages/web/src/lib/pagination/`, decoupled from audit so it's reusable by any future `(timestamp, id)`-ordered list.

## Org/scope sharing Phase 3 (org management backend)

Org/scope sharing **Phase 3 (org management backend)** opens the membership-truth WRITE path Phase 1 deliberately left closed (00012's comment: "only a service-role client can create orgs/memberships" until Phase 3) — see `.agent/claude/org-sharing-phase-3-org-backend/plan.md`. Every state transition (`createOrg`/`renameOrg`/`deleteOrg`, invite/accept/decline/revoke, `removeMember`/`changeMemberRole`/`leaveOrg`) is a **SECURITY DEFINER RPC** in `00022_org_management_rpcs.sql` — `orgs`/`org_members`/`org_invites` carry **no insert/update/delete RLS policy at all**; direct RLS-gated writes were rejected for two reasons: the **owner-bootstrap problem** (the first membership row can't be gated by existing membership, so a self-insert-as-owner policy would let anyone seize any org) and **non-atomic accept** (inserting the membership row and flipping the invite status must happen in one transaction, not two RLS round-trips). Unlike `memory_write`/`memory_delete` (Phase 2, which take an explicit `p_user_id` because the edge `api_key` service-role client has no session JWT of its own), every Phase 3 RPC resolves the actor as `auth.uid()` directly — no RPC takes a caller-supplied user-id parameter — because these are dashboard actions invoked under a real Supabase user JWT session. **`00041_org_actor_override.sql` revises exactly this point for the 8 RPCs the REST `orgs` function calls** (see the dedicated Key decision below): they gain a trailing `p_actor_user_id` that is honoured ONLY on a verified `service_role` connection, so the "no caller can name a different identity than the one that authenticated" property is preserved verbatim while the api_key tier becomes serviceable. `_invite_accept`/`_invite_decline`/`_leave` keep the pure `auth.uid()` form. This is the concrete form of the anti-TOCTOU fix: `lorekit_org_invite_accept(p_invite_id)` reads the invite, matches its `invitee_email`/`invitee_handle` against the CALLER's verified JWT claims (`email`, `user_metadata.user_name`) via the shared `lorekit_invite_addressed_to_caller` helper, and only ever inserts `org_members(org_id, auth.uid(), role)` — the invited string is a match target, never the membership subject, so a forwarded invite can only ever be redeemed by the identity it's actually addressed to. `lorekit_invite_addressed_to_caller` explicitly `coalesce`s each side of the identity check to `false`: `NULL = x` is SQL `NULL`, not `false`, and an un-coalesced `or` between a matched email and a NULL handle evaluates to `NULL` — which `if not (...)` treats as `if not false`, silently skipping the authorization exception. This was caught live by `migrations.test.sql`'s AC-6 negative assertion (a different authenticated user accepting a same-org invite) during Phase 3 development and is exactly the kind of bug an SQL-level assertion suite (not just the mocked TS unit tests) exists to catch. `lorekit_org_can` (00015) is **extended, never re-derived**, with six management capabilities (`invite`/`revoke_invite`/`remove_member`/`change_role`/`rename_org`/`delete_org`); capability-independent invariants a static role matrix cannot express (an admin may act only on `member`/`viewer` targets, never `owner`/`admin`; the last remaining owner can never be removed/demoted/left) live as `plpgsql` guards inside the RPC bodies themselves. `org_invites.role` CHECK excludes `owner` outright (ownership is non-transferable in v1) and `rls_org_members_select` is widened from own-row-only (00012) to all co-members of a shared org via `lorekit_org_role`. Dashboard server actions (`orgs.ts`, `org-invites.ts`) mirror `tokens.ts`/`webhook-secrets.ts` exactly — Supabase user JWT + RLS reads, `.rpc()` writes, non-throwing `recordAuditEvent` — and NO dashboard UI ships this phase; the Settings → Organization page, member list, invite form, and accept/decline card are the next stacked PR (Phase 4), per `ux-design.md`.

## Safe org deletion

**Safe org deletion** (`supabase/migrations/00025_safe_org_deletion.sql`) keeps the `memories.org_id` `ON DELETE CASCADE` (the #73 decision) and layers recovery ABOVE it: `lorekit_org_delete` becomes a **soft-delete** (stamps `orgs.deleted_at`), with a separate owner-only `lorekit_org_purge` for the real cascading delete (SQL-only for now — the `audit_log` action CHECK has no `org.purge` value, so a dashboard purge button would need a second CHECK migration; framed as the explicit permanent-delete / grace-period-job path). A soft-deleted org's lore vanishes from **every** read through ONE change — `lorekit_member_org_ids` (the single tenant-visibility predicate, consumed by both the `memories` RLS policies and the mirrored `applyTenantScope`) now joins `orgs` and filters `deleted_at is null`; because callers read the function's *output list*, `tenant-scope.ts` and its drift guards are untouched. `rls_orgs_select` uses a direct `org_members` subquery (not the function), so it gets an explicit `deleted_at is null`; `rls_org_limits_select` routes through the function and is hidden transitively. Retention is a documented `ORG_DELETE_RETENTION_DAYS = 30` (no purge job yet). The dashboard delete flow gets a type-the-org-name `ConfirmDialog` (additive `confirmPhrase` prop) + an "Export lore" JSON download (`exportOrgLore`) offered before deletion.

## Scope→org binding

**Scope→org binding** (`supabase/migrations/00026_scope_org_bindings.sql`) lets an org admin bind a scope (e.g. a repo) to an org so writes under it auto-route to the org without each write naming it. Authorization stays server-derived (the Phase 2 rule): binding requires the new `manage_scopes` capability (`lorekit_org_can`, extended not re-derived, admin/owner); and a write under a bound scope routes to the org **only if the writer is a write-capable member** — a non-member's write **falls back to personal, never rejected**. `memory_write` (no explicit `p_org_slug`) consults `org_scope_bindings`, and its return grows additive `org_routed` + `binding_org_slug` columns so the edge `toolWrite` can attach an actionable `notice` ("saved personal; this scope is shared with `<org>`, ask an admin") — the graceful-personal-**and-informed** decision (never silent, never a hard reject). Explicit `p_org_slug` always takes precedence (binding lookup skipped). Binding is server-truth in `org_scope_bindings` (globally unique per scope), NOT the advisory `.lorekit/config.json`. The Node/mcp-core path passes `p_user_id: null` (service-role) so it never binding-routes — fail-safe. **This is the backend + MCP routing only; the dashboard "Settings → Shared scopes" UI + Explorer bound-scope badge are the stacked follow-up.**

## GitHub App single-secret model

**GitHub App single-secret model** (`supabase/migrations/00037_github_installations.sql`, `supabase/functions/mcp/webhook.ts`): ALL App-delivered events are HMAC-verified against the ONE `GITHUB_APP_WEBHOOK_SECRET` — ZERO `webhook_secrets` rows are written for App-covered repos. The App path is dormant until `GITHUB_APP_ENABLED=true` (env/Supabase secret). Fail-safe pending-identity: a GitHub member with no LoreKit account → `status='pending'`, `user_id NULL`, never dropped; a later login transitions to `status='linked'`. Idempotent upsert via `UNIQUE (installation_id)` + `ON CONFLICT DO UPDATE`. `lorekit_find_user_by_github_id` is a SECURITY DEFINER function that bridges PostgREST's auth-schema limitation (queries `auth.identities` directly). The `?state=` setup-URL return bounce is correlation-only — never grants access; authorization is always `auth.uid()` + RLS. **Dashboard visibility is NOT gated on the webhook**: the webhook was the ONLY row-creator, so an install with `GITHUB_APP_ENABLED` off (or a missed delivery) showed on GitHub but `0` in LoreKit forever — `handleSetupReturn` was link-only and couldn't create the row. The fix is the `installations/sync` edge endpoint (`installation-sync.ts` + `github-app-client.ts` + the pure `github-app-jwt.ts`): the Setup-URL bounce records the install directly via an App JWT, decoupled from `GITHUB_APP_ENABLED` (which still gates only the webhook branch). The App private key stays a Supabase secret — never Vercel/browser — because the fetch happens edge-side; entitlement reuses the webhook's own-account rule (org installs stay `pending`, a documented follow-up). Post-merge runbook in `docs/github-app.md`.

## Hook scope ordering unified (project scope injected)

**Hook scope ordering is unified, and project scope IS injected (reverses the earlier exclusion).** The pre-existing decision that `deriveScope().readOrder` (the hook's injected/resolution set) deliberately EXCLUDED `project::` — so the hooks and `tree` never surfaced project-scoped lessons — is **REVERSED as of the smart-hooks PR**. `readOrder` is now `[projectScope, branchScope, repoScope, 'global']` (null-filtered, deduped), matching the read commands' `scopeList` EXACTLY — one scope ordering everywhere (hook, `tree`, `list`/`search`/`stats`/`diff`/`lint`/`dedupe`), project most-specific so a project lesson wins and is injected. **Accepted caveat:** the offline store keys `project::` by the working directory's **basename** (`scopeToDir` → `project/<basename>`), so two unrelated repos that happen to share a folder name can cross-surface each other's project-scoped lessons — accepted as the out-of-the-box-completeness tradeoff (the alternative, excluding project entirely, left project lessons silently un-injected, which was worse). The hosted/remote store scopes `project::{name}` server-side and is unaffected.

## Hook precedence + match is single source of truth with read commands

**The hook's precedence + match logic is a single source of truth with the read commands.** `fetchLessons` (SessionStart hot path) resolves cross-scope precedence via the pure `resolvePrecedence` (first-seen / more-specific-wins, `SCOPE_READ_LIMIT = 25`/scope as the FLOOR — the default read is the higher `scopeReadLimit(DEFAULT_SESSION_START_MAX_LESSONS)` = 100/scope — best-effort skip on a failed scope read; the injected set is then bounded from two directions — the `hooks.sessionStart.maxChars` CHARACTER BUDGET and the `hooks.sessionStart.maxLessons` LINE ceiling (default 100, range 3–200), whichever binds first; the old `MAX_LESSONS=15` count cap is retired and `source-hygiene.test.mjs` fails if it returns. **The ceiling is really a read-DEPTH dial**: at the default `maxChars` of 3000 the budget runs out around line 25, so what the number actually decides is the per-scope candidate fetch the ranker chooses from — the pure `scopeReadLimit` derives it as `clamp(ceiling, SCOPE_READ_LIMIT, MAX_STORE_LIST_LIMIT)`, i.e. 100/scope by default (400 across a four-scope hierarchy) rather than the newest 25. An earlier revision gated the growth to "only above the default"; that gate died with the default it keyed on, since once the default IS the depth, `ceiling > DEFAULT` can never fire inside the 3–200 range and the fetch would have been pinned at 25 while the ceiling asked for 100. `MAX_STORE_LIST_LIMIT = 100` is the `max(100)` that `ListMemoriesQuerySchema` — the schema validating `GET /memories`, NOT the `MemoryListSchema` MCP tool schema — enforces, mirrored self-contained per the `limits.ts` pattern, because an over-cap `limit` 400s and this best-effort path would swallow that into a silently EMPTY block) — the SAME function `tree` renders with — instead of a hand-rolled inline `byKey` merge, so the hook and `tree` provably can't drift. `resolvePrecedence` and `matchesQuery` were extracted from `lessons-view.mjs` into a new **dependency-free `packages/cli/src/lessons-pure.mjs`**, re-exported by `lessons-view.mjs` (so `search`/`tree` and every existing import/test are unchanged). The SessionStart read imports ONLY `lessons-pure.mjs` + `scope.mjs`, never the `util`/render/lint/dedupe surface — keeping the hot path lean while sharing one resolver. (`matchesQuery` was relocated alongside `resolvePrecedence` when the failure lookup was a client-side literal filter needing the exact same semantics as `search`. The failure lookup has since moved to `relevantLessonsFromStore`, which DELEGATES matching to the store — server FTS for remote, full-scope substring for local — via one multi-term `store.search`, deduping/capping the hits with the pure `dedupeRelevant`; the old client-side `relevantLessons` filter was removed once nothing called it. `matchesQuery` stays the shared primitive behind `search`, so co-locating it with `resolvePrecedence` still pays off.)

## CI/CD is split (ci.yml verifies, deploy.yml promotes)

CI/CD is split: `ci.yml` **verifies before merge** (PRs + non-main branches) — `check` runs mocked unit tests, `integration` boots a local Supabase and asserts the stack wires up (migrations apply, functions serve, authenticated MCP `tools/list` → 200) **and** runs `supabase/tests/migrations.test.sql` directly on Postgres — plpgsql `ASSERT`s over the SQL-only business rules (memory-cap + rate-limit triggers/RPCs, RLS user isolation, `memory_write` created_at insert-vs-conflict semantics, webhook-secret partial-unique + repo CHECK) that the mocked unit tests can only assume; the full CRUD `smoke.integration` round-trip runs in `smoke-staging` against a real project, not locally — the local edge runtime's older PostgREST can't resolve the `UNIQUE NULLS NOT DISTINCT` upsert arbiter for service-role writes. The web build/preview is covered by `ci.yml`'s `web-test` (Storybook) and `web-preview` (a Vercel preview deploy that posts a sticky status comment) jobs, both path-gated on `web`; Vercel's Git auto-deploy is off (`vercel.json` → `git.deploymentEnabled = false`). The preview job's BODY lives in `web-preview-deploy.yml`, a `workflow_call` reusable workflow — job-level orchestration (fork-secret guard, incremental redeploy decision, PR-head checkout, sticky comment) cannot live in the `vercel-preview-deploy` composite action, which has no `jobs:`. `ci.yml` calls it with `force: false` (quota-frugal) and `web-preview.yml` — a maintainer-gated `/web-preview` comment or a `workflow_dispatch` taking a PR number — calls it with `force: true`, which is the only way to redeploy an unchanged head. Do not re-inline the job into `ci.yml`: the manual path exists precisely because the incremental skip makes "Re-run jobs" a no-op. `deploy.yml` owns `main` and **deploys the already-verified commit** (no test re-run) as a **preview-first promotion pipeline** (deploy-preview → smoke-preview → deploy-production → smoke-production → rollback-on-failure; the pre-prod GitHub Environment is named `preview`). Tests run once, on the PR; the deploy path only smoke-tests the live deployment. Make `check` + `integration` required status checks — they are the sole gate keeping unverified code off main. Two Supabase projects, secrets scoped via `preview`/`production` GitHub Environments. Migrations are forward-only (expand/contract + PITR); only Edge Functions auto-rollback. `[functions.*] verify_jwt = false` in config.toml mirrors the deploy `--no-verify-jwt` flag and lets `supabase start` serve functions for the integration test. Do not re-merge the workflows or re-add a deploy-time test job — the split is what removed the old double test + double `db push`. See docs/deployment.md.

**The deploy SCOPE is measured against what is deployed, not against the previous commit.** `deploy.yml`’s `changes` job gates the API and web halves independently, and it used to diff a single push — justified as “lockstep only matters when both change, and then both halves run and flip together”. That holds only while every both-halves merge actually REACHES production. #492 changed both halves and its `smoke-preview` failed, so neither production job ran; #504 then changed only `packages/web/**`, reported `api=false`, and `promote-web-production` flipped the production domain to a bundle built from HEAD — carrying #492’s client, which POSTs `/functions/v1/memories/list`, a route the production edge functions had never been given. Every production Lore Explorer read answered 405 until the web was rolled back by hand. Each half is now diffed against the SHA it last reached production at, recorded by the advisory tags `deployed/api-production` / `deployed/web-production`. Only a SUCCESSFUL production flip advances a tag — and, symmetrically, each rollback job REPOINTS its tag at what production went back to (`rollback-production` at `HEAD~1`, the functions it just redeployed; `rollback-web-production` at the value `promote-web-production` captured before overwriting). Do not “simplify” a rollback into deleting the tag, or into not touching it: a marker left on a rolled-back SHA is still an ancestor of HEAD, so the non-ancestor rule never fires, and a deleted one falls back to `github.event.before` — the rolled-back commit itself. Both let the next merge skip a half production is not serving. Two exceptions, each deliberate: `rollback-web-production` DOES delete the tag when there was no previous promotion to restore — detection genuinely cannot cover that case, so it warns loudly and the next deploy of that half must be forced by hand — and `rollback-production` repoints only a marker THAT RUN advanced (the tag already names `github.sha`), because on a FAILED deploy nothing advanced it and writing `HEAD~1` would move it forward over work production never received. The tags fail OPEN — missing, or not an ancestor of HEAD, falls back to the push baseline; no baseline at all, or a git call that throws, means every tracked file and both halves — because a wrong `false` is that incident while a wrong `true` is one redundant deploy. The decision lives in the unit-tested `scripts/resolve-deploy-scope.mjs`, not in a shell block — `deploy.yml`’s `changes` job calls it, the two flip jobs advance the tags, the two rollback jobs repoint them, and ci.yml’s `deploy-scope` job runs its tests on every PR that touches it. Do not reinstate the single-push baseline. See docs/deployment.md → “The deploy scope is measured against what is DEPLOYED”.

## Smoke tests clean up after themselves

**Smoke tests clean up after themselves, and a sweeper cleans up after the runs that could not.** The live suites (`smoke.integration`, `memories-api.integration`, `orgs-api.integration`, `byod-smoke.integration`) write to REAL projects — staging in `smoke-preview`, production via `doctor --deep` — so any artefact that outlives its run is permanent pollution of a live tenant. Two things made that the default; both are fixed. **(1) The deletes were soft.** `memory.delete` / `DELETE /memories` ARCHIVE unless `force=true`, and `DELETE /orgs/:slug` is `lorekit_org_delete`, a SOFT delete since 00025 — so the MCP suite left two archived memories and the orgs suites left a soft-deleted org **per run**, the latter invisible to every RLS read (`lorekit_member_org_ids` filters soft-deleted orgs out) and therefore unreachable by any later API call. Cleanup now hard-deletes (`force=true`) and purges orgs via `lorekit_org_purge` (SQL-only, owner-gated, called through PostgREST with the suite's JWT); the org id is captured at CREATE time because a purge after the delete test cannot look it up. **(2) Cleanup was id-keyed.** The hooks deleted a hand-maintained list of ids captured mid-test, so a key whose test threw before its `createdId… =` line was never recorded and never removed (`…-force`, `…-org-id-form` and `…-audit` were never in the list at all). Every key/slug is now minted through `createSmokeNamespace` (`packages/mcp-server/src/smoke-cleanup.ts`), which registers it AT MINT TIME; `afterAll` sweeps the whole namespace and reports leftovers as a warning, never a thrown hook — a leak must be visible without turning a passing suite red. No in-process hook can cover a run that never reaches `afterAll` (crash, OOM, cancelled workflow, job timeout), so `scripts/smoke-cleanup.mjs` sweeps orphans by NAME PATTERN as an `if: always()` step after every smoke job. Four guards stand between it and real data: an anchored pattern over a **closed set of labels** (`memories-` / `byod-` / bare — a permissive `[a-z0-9-]*` prefix also matches real lore such as `how-to-debug-a-smoke-…-failure`, and this script DELETES what it matches, so `createSmokeNamespace` throws on an unregistered label); a `--min-age-minutes` guard (default 30) so a concurrently-running smoke suite is never swept out from under, measured from the SERVER's `updated_at` and not the client-minted name (the name's epoch comes from whatever machine ran the suite, so a runner >30m behind would mint names that look already-stale and get its live rows deleted mid-run — the name is the authority on RECOGNITION, the server on AGE); a refusal to run on a **service-role** `LOREKIT_SMOKE_TOKEN` without `--allow-service-role`, because service-role bypasses RLS and every handler skips its tenant filter for the `service` tier (`list.ts`/`remove.ts`/`lorekit_memory_scopes`), so a sweep on it spans EVERY tenant in the project — CI passes the flag because its stack is a single-tenant throwaway; and `--dry-run`. It exits 0 even on partial failure unless `--strict`, and every phase is individually try/caught so a **network error cannot reject at top level** — this is the last step of `smoke-production`, whose failure triggers `rollback-production`, and a DNS blip in a cleanup step must never redeploy the previous commit. The page walk runs to completion rather than stopping at a cap: paging is newest-first with no persisted cursor, so a cap that is hit leaves the OLDEST orphans unreachable on every future run too. Production gets the sweeper in `--dry-run` + `continue-on-error` only — nothing there should be minting smoke artefacts, so a non-empty plan is a signal to act on, not something to delete inside a rollback-gated job. The pattern is mirrored into the zero-dep script (which must run from a bare checkout, so it cannot import the module) and drift-guarded by `smoke-cleanup.spec.ts` — the `limits.ts` mirror pattern. `ci.yml` should run the sweeper with `--min-age-minutes 0 --allow-service-role --strict` against the throwaway local stack: that is the only place the sweeper ITSELF is exercised on every PR, so a broken filter fails there instead of silently no-opping against staging for months. **The workflow steps are documented, not committed** — the GitHub App that opens automated PRs has no `workflows` permission, so `docs/deployment.md` → "Wiring the sweep into CI" carries the three YAML blocks for a human to apply once. `doctor --deep`'s round-trip delete moved into a `finally` for the same reason (it runs against PRODUCTION on every deploy). Do NOT "simplify" cleanup back to a soft delete, to id tracking, or to a permissive name pattern.

## Org REST routes open to lk_* tokens, gated by token permission

**Org REST routes are open to `lk_*` API tokens, gated by token permission — NOT by auth tier.** Every route in `supabase/functions/orgs/` used to be `requires: 'jwt'`, so API tokens got a 403 and the CLI had to keep an MCP transport alive purely for `org.create`/`org.list`/`org.rename`/`org.delete`. They are now `requires: 'read'` (GET) / `requires: 'write'` (POST/PATCH/DELETE), using the router's existing `hasPermission` — `router.ts` is unchanged. A token's read/write permission is orthogonal to its holder's org role: a `lk_rw_*` token owned by a `viewer` still cannot rename an org, because `lorekit_org_can` is still the sole role→capability source. **Opening this required solving two independent problems, and skipping either one is a security bug, not a feature gap.** (1) **Actor resolution.** The api_key tier reaches Postgres over a service-role connection with no `auth.uid()`, so every `lorekit_org_can(auth.uid(), …)` denied. `00041_org_actor_override.sql` adds a trailing `p_actor_user_id uuid default null` to the 8 org RPCs the REST surface calls and resolves it through `lorekit_org_actor`, which honours the parameter **only** when `auth.role() = 'service_role'` — the same verified-JWT claim `rls_insert` (00001) has gated on since the first migration, set by PostgREST from a cryptographically verified token and never from request input. An `authenticated` caller's `p_actor_user_id` is discarded, so the Phase 3 anti-impersonation property is preserved exactly; the edge function derives the actor from the `api_tokens` row it matched by hash, never from the request body. Trailing + defaulted means PostgREST's named-argument resolution keeps every existing caller (all of `web/src/lib/orgs.ts`, `org-invites.ts`, `org-members.ts`, and the MCP `org.*` tools) working untouched. NULL actor fails closed everywhere; `lorekit_org_create` — the capability-free owner-bootstrap path — carries an explicit NULL-actor guard so service-role can never insert an ownerless org. `lorekit_org_invite_accept`/`_invite_decline`/`_leave` are deliberately excluded: accept/decline additionally match the invite against the caller's VERIFIED JWT identity claims, which service-role has no equivalent of, and giving it one is a separate change with its own threat model. The visible consequence is that "leave an org" over an API token fails closed with a 403 — documented at the call site and in the drift guard's exemption list, not silent. (2) **The read path.** `handleListOrgs` selected `org_members` with no filter and `handleGetOrg` selected `orgs` by slug with no membership check — both correct under RLS and catastrophic on the service-role client (`GET /orgs` would have returned every org in the database; `GET /orgs/:slug` any org by guessed slug). Every read now applies an explicit tenant predicate for `api_key` only, via `_shared/api/tenant.ts` (`applyOwnMembershipFilter` / `isOrgMember` / `hasOrgCapability`), mirroring how `memories/handlers/list.ts` already does it — membership truth stays `lorekit_member_org_ids`, capabilities stay `lorekit_org_can`, never a hand-rolled predicate. **A non-member gets the same `notFound('Organization')` as a non-existent slug**, on the mutating handlers' slug lookups too — a 403 there would leak org existence across the whole slug namespace. `GET /:slug/invites` returns an empty 200 to a member without the `invite` capability, exactly matching what `rls_org_invites_select_manage` gives a JWT member, rather than widening the tier. `auth.type === 'service'` is **never** special-cased into a filter: CI keeps full access, as in `memories`. Both properties are executable-guarded by `packages/mcp-core/src/org-actor-usage.spec.ts` (source scan, anti-vacuity floors, mutation-tested) and by `supabase/tests/migrations.test.sql` §50–§59, whose centrepiece is the negative case — an `authenticated` session passing another user's id as `p_actor_user_id` is denied on every RPC and mutates nothing. **The CLI has since cashed this in and dropped MCP entirely:** `packages/cli/src/store/remote.mjs` routes `orgCreate`/`orgList`/`orgRename`/`orgDelete` at `POST /orgs`, `GET /orgs`, `PATCH /orgs/:slug` and `DELETE /orgs/:slug` (slugs `encodeURIComponent`'d — they are path segments), `ping()` probes `/health` with no JSON-RPC fallback, and `_mcp`/`_mcpEntries` are gone. Each method's RETURN SHAPE is byte-for-byte what the MCP path produced, because `packages/cli/src/mcp-server.mjs` serialises them straight into a `tools/call` result — `orgCreate` reassembles `{ id, slug, name }` from the bare id string `POST /orgs` returns, and `orgDelete` synthesises `deleted: true` because `DELETE /orgs/:slug` is a 204. `packages/cli/src/mcp.mjs` is deliberately NOT deleted: it still backs the `lorekit mcp` stdio server and exports `mcpToRestBase`/`restFetch`. Three guards keep the transport from creeping back: `rest-route-parity.spec.ts` (every `_rest(...)` call resolves to a registered route in the named function's `index.ts` — it resolves `orgs` as well as `memories`), a source-scan assertion that `remote.mjs` contains no `mcpCall`/`_mcp(` reference, and per-method URL/method/body assertions in `packages/cli/test/unit.test.mjs`.

## Org-owned lore archive/hard-delete over REST

**Org-owned lore can be archived and hard-deleted over REST, through the same role-gated RPC MCP uses.** `DELETE /memories?scope=…&key=…&org=<slug>` routes to `memory_delete` (`00020_memory_delete_org.sql`) with exactly `toolDelete`'s argument set (`p_user_id`, `p_org_slug`, `p_scope`, `p_key`, `p_force`) instead of a direct `.delete()`/`.update()` — the api_key tier's service-role client bypasses RLS, so a raw query against an org-owned row would skip the `lorekit_org_can` gate entirely. That was the last memory capability MCP had and REST did not. The RPC is keyed on the NATURAL key and has no id parameter, so `/memories/:id` + `?org=` is a 400 rather than a silent fall-through that would delete the caller's personal row while they believed they were deleting the org's. `LK002` is translated at the call site via `translateDbError` (403), never left to a generic error path. The audit action is chosen from what the RPC reports it DID (`deleted` vs `archived`), not from the requested `force`, and carries `org` in metadata — mirroring `toolDelete`. **`memory.restore` gets no org branch, because MCP has none either** (`toolRestore` is a plain `.eq(user_id, …)` update); inventing one on the REST side would put the two surfaces out of parity in the opposite direction. Restoring org-owned lore is an open gap on BOTH surfaces.

## Usage analytics answer record-level questions

**Usage analytics answer record-level questions, and the write side stays fail-safe.** `GET /memories/usage` reports both CALL counts (`event_count`/`reads`/`writes`) and RECORD counts (`record_count`/`records_read`/`archived`/`expired`) — the distinction is deliberate: "you read 600 memories today" is a RECORD figure (`records_read`), not the number of read calls, so a single `memory.list` returning 600 rows counts once as a call and 600 as records. Record counts are populated by two optional headers threaded through the ONE recording site on each surface (`_shared/api/router.ts`, `mcp/mcp-handler.ts`), never per-handler: the collection read handlers set `X-LoreKit-Result-Count` (read once by the router; MCP derives the same via `countRecords`), and both surfaces read an inbound `X-LoreKit-Correlation-Id` (a bounded PR/session/job key, validated by the pure `parseCorrelationId`) so `?correlation_id=` can scope "usage for this PR". Both are **fail-safe by contract** — a malformed count or correlation degrades to null and never fails the request it is measuring, the same posture as `recordUsageEvent` itself. **Expiry is event-sourced through the purge, not through reads:** a lazy read filters expired rows but never deletes them, so there is no discrete expiry moment there; `purge_expired_memories` (00045) instead records one `memory.expired` event carrying the count it deleted (previously discarded), and `expired` sums those. **Archived is the caller-driven lifecycle counterpart:** `archived` counts `memory.archive` EVENTS in the window (`event_count`, one call = one memory) — NOT `record_count`: the DELETE handler does now set `X-LoreKit-Result-Count` on both its personal and its `?org=` branch, but only for rows written from that point on, so every historical archive row is still null and summing records would under-report the window; an activity figure, not a live archived-total. **The record/effect counters count only what happened:** `records_read`, `archived` and `expired` are summed only over rows whose `outcome` is `ok`, so a refused archive (403 `permission_denied`, 404 `error`) stays a write CALL without being reported as a retired memory. A dry-run answers 200 and so is still counted — `usage_events` carries no dry-run marker to tell it apart. The Explorer's Lifecycle card pairs the two. **Client contract for correlation:** the `lorekit` CLI auto-emits the header from `LOREKIT_CORRELATION_ID` (`restFetch`/`normalizeCorrelationId`); a hook or CI job exporting that var to the PR ref / session id tags every subsequent call — wiring a specific hook to export it is the one remaining client-side step. Like `GET /scopes`, the endpoint is REST-only (an aggregate read has no scope-keyed MCP tool) and its `usage_events.tool_name` is `memory.usage`.

## The Explorer's Activity panel has a DISPLAY default, separate from the list's

**The Lore Explorer's `?range=` has two defaults, and the split is the point.** The LIST still opens on all time — a list's job is to show everything, and that is what every existing `/lore` deep link (and `lorekit link` URL) has always meant by an absent `range`, so narrowing that default would silently re-scope every link already in the wild. But the ACTIVITY panel above it opens on the **last 24 hours**: a lifetime total has no preceding window to compare against, so every trend chip and sparkbar in the panel is meaningless under an unbounded selection, and the four numbers read as constants. `ExplorerInsights` therefore substitutes `DEFAULT_STATS_RANGE = {preset:'24h'}` for a `null` range when handing a value to the picker and the cards, and — the load-bearing half — **never writes it back**. It is a display default, not a filter; the list is untouched until the reader actually picks a range, at which point the selection means what it has always meant and narrows both.

That is only expressible because "has not chosen" and "chose All" became two different values: **`RangePicker` emits `{preset:'all'}` for All, not `null`.** Both resolve to the same unbounded window through `resolveRange`, so nothing downstream can tell them apart and nothing downstream needs to — but the substitution above has to, or clicking All would land back on the untouched value and the panel would snap to 24h instead of honouring the choice. The same reasoning governs the two other places a range is cleared: the Explorer's "View all time" empty-state action and clearing the `DateRangePicker` both emit `{preset:'all'}` rather than `null`. Do NOT "simplify" the All arm back to `null` — it reads as dead code and it collapses the two states.

## Dashboard figures COUNT to a new value

**Every stat figure on the dashboard is an `AnimatedNumber`, and the count is a change indicator rather than decoration.** The selections driving these numbers change constantly (a scope chip, a filter pill, a range preset) and the panel's held-frame rule deliberately keeps the previous render on screen while the next query resolves — so without the count, four figures quietly became four different figures and nothing said which had moved. The tween is ~400ms (an acknowledgement, not a countdown) and writes ONE text node directly instead of going through `useState`, so a 60fps text change does not re-render the card, its sparkbar and its tooltip sixty times a second.

Two consequences worth knowing before touching it. **The element renders two nodes**, a visible `aria-hidden` half the tween owns and a `sr-only` half carrying the settled value — a single node would expose whatever intermediate number assistive tech happened to read, so any test or caller reading a figure must read the `.sr-only` half, never `textContent` (which concatenates both). And **it honours `MotionConfig`'s `reducedMotion="always"` as well as the device preference**, deliberately NOT Motion's exact precedence: `MotionConfigContext` defaults to `'never'` with no provider mounted and this app has no root `MotionConfig`, so honouring `'never'` would let a default override a real user preference. `'always'` can force reduction; nothing can force motion on. That is also what makes the committed visual baselines deterministic — `.storybook/preview.tsx` sets `reducedMotion="always"`, so a story is screenshotted at the settled value instead of mid-count.

## MCP org tools serve `lk_*` tokens, on the same actor override REST uses

**The MCP `org.*` tools accept API tokens, and the two surfaces stopped disagreeing about who may manage an org.** They were JWT-only for a real reason — their handlers called the org RPCs without naming an actor, and those RPCs derive one from `auth.uid()`, which is NULL on the service-role connection an api_key caller gets, so every `lorekit_org_can(...)` denied. `00041_org_actor_override.sql` fixed the underlying problem by giving the eight org RPCs a trailing `p_actor_user_id` honoured **only** on a verified `service_role` connection, and the REST `/orgs` routes have served tokens through it since. MCP was simply left behind, and `docs/mcp-tools.md` told readers to prefer REST "when you are authenticating with an API token" — a workaround documented as a recommendation.

Three things had to be true together, and skipping any one of them is a security bug rather than a missing feature. **(1) Permission gating.** `org.list` is `read`, the three mutations are `write`, enforced through the same `toolRequires`/`canRead`/`canWrite` path the memory family uses — so the dispatcher has exactly one permission gate instead of one gate and one auth-tier refusal. **(2) The actor is threaded, never inferred.** The dispatcher passes the resolved `userId` (null for JWT, the token owner for api_key) and each handler forwards it as `p_actor_user_id`; a NULL actor still fails closed, so an edge bug that forgot to pass it denies rather than acting as somebody. **(3) Every raw table read carries its own tenant predicate,** because on the api_key path there is no RLS to fall back on. `toolOrgList` adds `.eq('user_id', userId)` — without it a service-role read returns every membership row in the database — and `resolveOrgId` resolves the slug **through** `org_members` rather than with a bare `.from('orgs').eq('slug', …)`, which on a service-role client is an existence oracle for any guessable slug, answered before any RPC can deny anything. A non-member now gets the same "org not found" a non-existent slug gets. `org-actor-usage.spec.ts` grew an MCP arm asserting all three, and `migrations.test.sql` §86 proves the RPC side end to end.

**Token permission is not an org role and does not become one.** A `lk_rw_*` token held by a viewer passes the permission gate and is then denied the rename with `LK002`, because `lorekit_org_can` inside the SECURITY DEFINER RPCs remains the only role→capability source. The edge can only check the key; the database checks the person. Both gates apply and neither substitutes for the other — §86's viewer case exists to keep that true.

**Open, deliberately: a scope-restricted token can still administer orgs.** A key with a scope allowlist can create, rename and soft-delete orgs, on MCP exactly as on REST, which has behaved this way since the org routes opened. The scope machinery was built for lore and orgs carry no scope to match against, so there is nothing to compare. There is a real argument the other way — `_shared/account-wide-tools.ts` refuses an account-wide *sweep* to a scoped key on the reasoning that "a key narrowed to one repo has no business sweeping the account", and deleting an entire org is at least as consequential. This change deliberately does **not** answer it, because answering it on MCP alone would reintroduce exactly the surface divergence being removed here: the fix, if it is one, belongs on REST and MCP together. Recorded so the next person finds a decision rather than an oversight.

## Dashboard analytics reads stay REST-only

**`GET /memories/usage`, `/tags`, `/facets`, `/activity` and `/read-activity` have no MCP tool and no CLI command, and that is a decision rather than a gap.** They are dashboard telemetry: usage rollups, tag facets and activity heatmaps, keyed by `scope_type` or by tag/time bucket, which the web app renders into charts and drill-downs. An agent's job is reading and writing *lessons* — the `memory.*` CRUD plus `memory.list order=rank` for "what is worth reading" — and no loop in this repository consumes an aggregate.

The cost of adding them is not zero, which is the actual argument. Every entry in `tools/list` is context the model pays for in **every** session and one more choice it can get wrong, so five analytics tools that nothing calls is negative-value surface area. Three of them are also name-bearing (`tags`, `facets`, `activity` return scope and label STRINGS, which embed repo and project names), so an MCP twin would have to pass `p_key_scopes` to stay inside a restricted key's allowlist — `usage` is the only one exempt, because it rolls up by `scope_type` and emits no scope name at all. That is a real scope-leak surface to take on for a capability nobody asked for.

Nothing forces them on, either: the completeness gate requires a **catalogued MCP tool** to have a CLI command or a declared exemption, and these were never MCP tools. `rest-tool-name.ts` already names them for usage aggregation, which is the only cross-surface coupling they have, and it is satisfied. `/relevant` is the one that looks like a sibling and is not — it is already covered, by `memory.list order=rank` on MCP and `remote.relevant()` in the CLI hook path.

If this is ever revisited, the answer is **not** five tools. It is at most ONE compact `memory.stats` rollup, and `lorekit stats --tags` / `--activity` flags rather than new top-level commands, so the agent-facing surface grows by one entry instead of five.

**The decision is annotated in code, not only here.** Each of the five is a `restOnly` entry in `packages/mcp-core/src/telemetry-vocabulary.ts` — the closed set of names `usage_events.tool_name` may carry — so the omission is a declared, guarded field rather than an absence a future audit reads as a gap. `telemetry-vocabulary.spec.ts` pins the five by name, pins `memory.relevant` as explicitly NOT one of them (it looks like a sixth; it is already covered by `memory.list order=rank` and `remote.relevant()`), and scans the CLI sources to prove no command calls the five — using the `/memories/relevant` call that IS there as the anti-vacuity floor, so a broken scan fails rather than passing on nothing. The same spec asserts this section still exists: the field says which, this record says why, and losing either leaves the other unexplained.
