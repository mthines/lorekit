# Storybook — component/page stories, MSW mocking, and Vercel deploy

The `@lorekit/web` dashboard ships Storybook 10 (`@storybook/nextjs-vite`) wired to
Vitest **browser mode** via `@storybook/addon-vitest`. Every story is a test:
`play` functions become interaction tests and every other story is screenshotted
for visual regression. This doc covers the **MSW-mocked full-page stories** and how
to **deploy Storybook to Vercel** as a second project. For the base wiring and the
two-file convention, see the "Web Storybook tests" section of the root
[`CLAUDE.md`](../CLAUDE.md).

## Two-file convention (recap)

Per component/page, two files:

- `<name>.stories.tsx` — visual-regression stories (`Default` + a second story).
  Screenshotted by the `afterEach` in `.storybook/vitest.setup.ts`. Baselines are
  committed under `src/**/__screenshots__/**/*-chromium-linux.png`.
- `<name>.test.stories.tsx` — interaction tests under the `/Tests` namespace
  (`tags: ['test']`, `chromatic.disableSnapshot`). Their `play` functions run in
  the browser; they are **not** screenshotted.

## MSW-mocked full-page / full-view stories

The dashboard standardises on `@tanstack/react-query` v5. Query hooks fetch through
the Supabase **browser** client (`@/lib/supabase/client` → PostgREST over HTTP).
[MSW](https://mswjs.io) mocks those HTTP responses so a page renders a realistic,
stable dataset with no live backend — and so the **deployed** static Storybook works
too (the service worker, `packages/web/public/mockServiceWorker.js`, is committed and
shipped in the build).

Pieces (all under `packages/web`):

| File | Role |
|------|------|
| `public/mockServiceWorker.js` | MSW service worker (generated by `npx msw init public --save`; committed so hosted stories mock too) |
| `src/mocks/memories.ts` | Fixtures + `memoryHandlers()` — mocks `GET /rest/v1/memories` and `/auth/v1/user`; exports `FROZEN_NOW` |
| `src/mocks/decorators.tsx` | `withQueryClient` (test `QueryClientProvider` — retries off, no refetch), `withFrozenClock` (pins `Date` for deterministic time-relative renders), `withMemorySidebar` (context the `/lore` tree needs) |
| `.storybook/preview.tsx` | `initialize()` + `mswLoader`, injects the public Supabase URL, and neutralises `motion` animations for stable snapshots |
| `.storybook/main.ts` | `staticDirs: ['../public']` so the worker is served at `/mockServiceWorker.js` |

A story opts in via `parameters.msw.handlers` and the decorators:

```tsx
const meta: Meta<typeof DashboardStats> = {
  title: 'Pages/Dashboard Stats',
  component: DashboardStats,
  parameters: { layout: 'fullscreen', msw: { handlers: memoryHandlers() } },
  decorators: [withFrozenClock(FROZEN_NOW), withQueryClient],
};
```

Shipped examples:

- **`src/app/(dashboard)/lore/LorePage.stories.tsx`** — a *true full-page* story of the
  `/lore` client page. Its scope tree + 26-week contribution heatmap resolve from the
  MSW-mocked PostgREST reads. Needs `parameters.nextjs.appDirectory: true` (the page uses
  `useRouter`/`useSearchParams` via `useUrlState`).
- **`src/components/dashboard/DashboardStats.stories.tsx`** — a full-view story of the
  Overview page's main content. `/overview` is a **server component** (it `await`s the
  Supabase *server* client, so it can't render in the browser), so the largest *client*
  subtree is storied instead — the guidance for any RSC page.

### Rendering-model note

Client pages (`'use client'`) render as true full-page stories under MSW. Server-component
pages cannot — story their largest client subtree, don't refactor an RSC page to client just
to story it. One honest edge: the `/lore` lesson list reads the `listMemories` **server
action**, which is gated on `supabase.auth.getUser()`; with no session in the mocked browser
context it returns an empty page, so the results panel shows its empty state while the rest of
the page populates. Every part driven by a *browser* fetch is populated.

### Determinism

Time-relative UI (freshness labels, trend chips, the heatmap) is pinned with
`withFrozenClock(FROZEN_NOW)`; fixtures are dated relative to `FROZEN_NOW`. `motion`
entrance animations are collapsed to an instant in `.storybook/preview.tsx`. Never put a live
`Date.now()`/`Math.random()` in a fixture — that is the classic snapshot flake.

## Running locally

```bash
cd packages/web
# both suites (interaction + visual) in one browser run
npx vitest run --config vitest.storybook.config.ts
# only changed stories (what CI's web-test job runs)
npx vitest run --config vitest.storybook.config.ts --changed=main
# update baselines after an intentional visual change
npx vitest run --config vitest.storybook.config.ts -u
# interactive Storybook
npx storybook dev -p 6006
```

Invoke with **`npx`**, never `pnpm exec` / `pnpm run` / `nx run` — those wrap the process and
hold the Playwright browser child's stdio open, so the run never returns. Playwright is pinned
to `1.56.0` so local and CI pixels compare like-for-like; bumping it means regenerating
baselines with `-u` on Linux/Chromium.

## Updating baselines from CI (no local toolchain needed)

Baselines are Linux/Chromium PNGs generated with the pinned Playwright build, so a run on a
different OS or browser version produces pixels that will never match CI. When you can't (or
don't want to) reproduce that toolchain locally, the **Update visual baselines** workflow
(`.github/workflows/update-baselines.yml`) regenerates them on the same runner image and browser
build `web-test` uses, then commits **only** the changed screenshots straight back onto the PR's
branch. Two ways to run it against a specific PR:

- **Comment `/update-baselines` on the PR** (write-access users only), or
- **Actions ▸ "Update visual baselines" ▸ Run workflow**, entering the PR number.

It runs `vitest -u` over the whole suite, stages only files under `__screenshots__/` (matching
baselines are rewritten byte-identical and produce no diff), commits, pushes, and comments the
outcome on the PR. Two limits worth knowing:

- **Fork PRs are rejected** — `GITHUB_TOKEN` can't push to a fork branch, so regenerate locally
  and push from the fork instead.
- The baseline commit is pushed with `GITHUB_TOKEN`, which by design does **not** re-trigger
  workflows, so `web-test` won't auto-run on it. Push a follow-up commit (or swap in a PAT) if you
  need CI to re-verify.

## Deploying Storybook to Vercel (separate project, Git integration)

Storybook deploys as its **own** Vercel project on the same repo, alongside the dashboard
project — no CI job and no `VERCEL_TOKEN` (native Git integration). Every branch gets a preview
URL that serves the stories, and each interaction test is inspectable in Storybook's
**Interactions** panel.

`packages/web/vercel.json` already belongs to the **dashboard** project (Next.js → `.next`), so
the Storybook project must **not** reuse `packages/web` as its Root Directory (it would inherit
the Next.js build). Point it at the **repository root** instead and set the build explicitly:

| Vercel Project Setting | Value |
|------------------------|-------|
| Root Directory | `.` (repository root) |
| Framework Preset | Other |
| Install Command | `pnpm install --frozen-lockfile` |
| Build Command | `pnpm --filter @lorekit/web build-storybook` |
| Output Directory | `packages/web/storybook-static` |

Steps:

1. **New Project** in Vercel → import this repository (a repo can back multiple Vercel projects).
2. Name it e.g. `lorekit-storybook`.
3. Set the five settings above (Framework Preset **Other** matters — it stops Vercel from
   auto-detecting Next.js).
4. No environment variables are required: `.storybook/preview.tsx` injects the public Supabase
   ref and MSW intercepts every request, so nothing reaches a real backend.
5. Deploy. Production tracks `main`; every branch/PR gets its own preview URL. Open a story and
   the **Interactions** panel replays that story's `play` steps against the deployed build.

The `build-storybook` script (`storybook build` → `storybook-static/`) is the same one Vercel
runs; verify locally with `cd packages/web && npx storybook build`. `storybook-static/` is
gitignored.
