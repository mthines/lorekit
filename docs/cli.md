# `@lorekit/cli` — command reference

The full role/behaviour description for the `@lorekit/cli` package (`packages/cli/`), extracted from the root [`CLAUDE.md`](../CLAUDE.md) Package map. The CLAUDE.md row keeps a terse command list and links here.

## Command surface

Zero-dep Node CLI: `install` (scaffolds the `lorekit-memory` + `lorekit-setup` + `lorekit-groom` skills, MCP server, and the deterministic lifecycle hooks into `.claude`/`~/.claude` per a project/global prompt — the plugin's three parts without a marketplace. **The hooks are an explicit choice, not a silent side effect**: a second prompt offers `all` (`SessionStart`, `UserPromptSubmit`, `PostToolUseFailure`, `Stop`) / `read-only` (`SessionStart` only) / `none` (`HOOK_MODES`/`hookEventsForMode`/`hookModeFromEvents` in `config.mjs`), preselected to the DETECTED state via `installedHookEvents` — the same reader `doctor` uses — so a fresh install preselects `all` while a re-run never resurrects hooks the user declined. `--hooks <mode>` selects non-interactively and bypasses the already-installed short-circuit; `--hooks none` REMOVES wired hooks whereas the older `--no-hooks` stays skip-only. `upsertClaudeHooks` takes the event list and PRUNES lorekit entries for events outside it, so `all → read-only` is a real downgrade. It is also CONVERGENT — an event carrying SEVERAL lorekit entries keeps exactly ONE (the first updated in place, every further one deleted and reported as `deduped`), because reconciling only the first left a duplicated `settings.json` firing the hook twice forever and made `install --force` unable to repair the state it is most often run against. `LOREKIT_HOOK_RE` decides what counts as ours, so it tolerates a leading path/quote, a pinned `@lorekit/cli@x.y.z` and a `.cmd`/`.exe` suffix (a form it MISSES is appended alongside, which is how the duplicates were born) while requiring a leading boundary so an unrelated `mylorekit hook …` is never claimed. `install` returns the `{ exitCode, ... }` shape carrying a bounded `lorekit.cli.hooks_mode`; an INTERACTIVE `--force` prompts keep/replace/remove for an already-configured token instead of silently reusing it — the pure `tokenPlan` decides, and a non-interactive run still reuses), `doctor` (connectivity/token/scope health checks; `connectivity` probes the PUBLIC `/health` function and therefore proves only the network path, so a separate `authentication` check calls `RemoteStore.verifyAuth()` — one authenticated `GET /memories?limit=1` — and FAILS on a 401 revoked/deleted token, PASSES a 403 as accepted-but-unpermitted [a healthy `lk_wo_*`], and never turns a 429/5xx/network error into a revoked verdict), `list` (alias `ls` — read-only human view of the lessons for the cwd's scopes, project/branch/repo/global, split into an **Offline** local-store section and a **Remote** hosted section that degrades gracefully when unconfigured; `--json`/`--scope`; `--all` drains all pages via `gatherStream` [default is single-page `gather()`]; `--max <n>` hard-caps entries surveyed [default 5000]; `--since`/`--until <iso-date>` forward `created_since`/`created_until` to the REST request; independently builds BOTH stores via `src/stores.mjs` + renders via the reusable `src/lessons-view.mjs`, the seam all the `search`/`show`/`stats`/`diff` read commands stack on; the shared deny-wins block those five read commands all use is extracted into `resolveDenies(root,{env})` in `control.mjs`), `search` (alias `grep` — full-text search the same scopes/stores/split as `list`; matches a **literal, case-insensitive** substring against a lesson's key OR value, via the pure `matchesQuery` (in the dependency-free `lessons-pure.mjs`, re-exported by `lessons-view.mjs`)/`filterGroups` helpers over the shared `gather()` output — NOT each store's native `search` method, whose semantics diverge (local literal-substring vs remote server-FTS); regex metachars are matched verbatim, never compiled; `--json`/`--scope`), `show` (inspect ONE lesson in full via each store's real `read({scope,key})` — complete untruncated value, scope, key, updated, tags, and which store(s) hold it; when the same `scope::key` is in both stores it shows both and flags any divergence via the pure `recordsDiverge`; exits non-zero when found in no readable store; `--json`), `stats` (at-a-glance counts of the applicable lessons **per scope** and **per store**, with per-store + grand totals, in the same Offline/Remote split; **remote counts come from `GET /memories/scopes` via `RemoteStore.listScopes()`** — the same Postgres aggregate `scopes` uses — NOT from row-draining `memory.list`, so the count is exact for any scope size; Offline tallies via pure `tallyGroups` over `gather()`; `--json`/`--scope`), `scopes` (a **store-wide** inventory — UNLIKE every other read command, NOT cwd-scoped: enumerates EVERY distinct scope present in the store with a per-scope non-archived count, so a user sees all scopes they have lessons in anywhere; pure `scopeTypeOf`/`sortScopeInventory`/`filterScopeInventory`/`summarizeScopeInventory` in `lessons-view.mjs`, sorted by scope type then name; `--json`/`--scope` [a **substring filter** over the inventory, not a single-scope selector]. **Offline enumeration is exact** — a new `LocalStore._walkEntries()`/`listScopes()` (+ `TwoTierStore.listScopes()` deduping by `scope::key` across tiers, project shadowing home) recursively walks the store and reads each file's frontmatter `scope` string, NEVER reverse-mapping the on-disk layout [which is lossy for `project::{name}`, stored by basename only], so scopes are reconstructed verbatim. **Remote enumeration is exact too** — `RemoteStore.listScopes()` calls `GET /memories/scopes`, which aggregates one `{scope,count}` row per scope in Postgres [`lorekit_memory_scopes`, migration 00039], so the Remote section renders a REAL inventory through the same `filterScopeInventory`/`summarizeScopeInventory` helpers as Offline; a denied/unconfigured/unreachable/erroring remote degrades to a short, accurate note via the shared `describeError` at exit 0 [the old `REMOTE_SCOPES_UNSUPPORTED` sentinel is gone — the surface supports enumeration now]), `diff` (compare offline vs remote for the applicable scopes and report **local-only** / **remote-only** / **conflicting** keys grouped by scope, via the pure `diffGroups` set-diff reusing `recordsDiverge`; needs BOTH stores readable — an unconfigured/denied store yields a clear `comparable:false` note at exit 0, never a crash; `--json`/`--scope`), `tree` (alias `resolve` — the scope **precedence hierarchy**: resolves the hook-injected `readOrder` scopes [project→branch→repo→global, most-specific first] and marks per key which scope's lesson **wins** and which are **shadowed**, mirroring `core/lessons.mjs`'s first-seen-wins merge EXACTLY via the SAME shared pure `resolvePrecedence` [now in the dependency-free `lessons-pure.mjs`, re-exported by `lessons-view.mjs`]; per-store; `--json`/`--scope`), `lint` (flag low-quality lessons across the applicable scopes/stores — pure `LINT_RULES`/`lintEntry`/`lintGroups`: **empty-value**/**short-value**/**untrimmed-value**/**empty-key**/**volatile-key** [a per-sighting identifier in the key — a 6+ digit run or a segment-anchored `pr<n>`/`issue<n>` — which never collides, so the upsert never dedups and `seen_count` stays frozen at 1; conservative by design so `oauth2`/`sha256`/`wcag22`/semver never fire, with an embedder-only `{ volatileKeyAllow }` opts hatch mirroring `short-value`'s `minValueLen`, no config key]/**malformed-scope** [via the canonical `scopeIssue` validator], each rule independently tested; **exits non-zero when any finding exists** so it's a CI gate; `--json`/`--scope`), `dedupe` (heuristic near-duplicate detection — pure `tokenize`/`similarity` [zero-dep **Jaccard word-token overlap**, NOT embeddings]/`clusterDuplicatesBlocked` [inverted-index token-blocking, O(candidate_pairs) not O(n²), produces identical clusters to the oracle `clusterDuplicates` when Jaccard ≥ threshold > 0]; population is capped at 2000 entries for memory safety — when the cap is hit, a narrowing warning is printed; `--key-prefix` and `--since` narrow the population; **`--cluster-by-key <regex>`** switches from value-overlap to KEY-shape clustering [pure `compileKeyPattern`/`clusterByKeyPattern`: entries whose keys share the same first capture group — or full match — of the regex form one family, catching coordinate-key debt like many `pr{N}-{commentId}` rows for one comment that the Jaccard heuristic misses when values differ; a bare flag or unparseable regex is a usage error at exit 1, and so is combining it with an explicit `--threshold` (key mode has no similarity cutoff, so the flag would otherwise be silently ignored — a repo-level `dedupe.threshold` stays a value-mode default and never breaks a key-mode run); `--json` reports `mode:"key"` + `keyPattern` and each cluster carries `keyGroup` instead of a similarity range]; per-store across scopes; `--json`/`--scope`/`--threshold` [default 0.8]), `link` (alias `url` — print a shareable dashboard **deep-link URL** to stdout, nothing else, so it pipes into a clipboard/PR/Slack: no-arg → the cwd's most-specific scope, `<scope>` → the scope-filtered Explorer, `<scope> <key>` / `<scope::key>` → a lesson detail-sheet link setting BOTH `?lesson=` and `?scope=`, with `--key` naming a key that itself contains `::` (the same escape hatch `show`/`write` have); filter flags mirror the Explorer [`--q`/`--owner`/`--range`|`--from`|`--to`/`--archived`], `--base`/`LOREKIT_APP_URL` override the host [default `https://lorekit.io`], `--json` → `{ url, surface, base, params }`. The read commands `show`/`search`/`list`/`tree` also take a `--link` flag that short-circuits to the equivalent URL for the current invocation. All URLs are built by the dependency-free **`src/deeplink-pure.mjs`** [the `lessons-pure.mjs` zero-import precedent], which encodes every param `encodeURIComponent(JSON.stringify(value))` and omits any param equal to its `useUrlState` default — the exact inverse of the web app's read [`packages/web/src/lib/hooks/useUrlState.ts`], mirroring `ScopeHealthCard.tsx`. `core/lessons.mjs`'s `writeConfirmation` [the hook link] now delegates to that module, **fixing a real bug**: it previously raw-encoded `?scope=<scope>`, which the dashboard's `JSON.parse` rejected into an all-scopes fallback; write-confirmations now deep-link to the exact lesson), `migrate` (relocate a LoreKit-format local store, or push one to the hosted store — `--from <path>` is required and the source is read by each file's frontmatter `scope`, so the source layout need not match the destination. `--to home|project` forces a single local tier and the default routes each entry by scope through the two-tier store; **`--to remote` pushes the source store up to the hosted one**, which is the local→remote transition that previously had no bulk path. Dry-run by default with a per-scope add/update/noop report; `--yes`/`--apply` writes; idempotent — a re-run is all-noop. The remote destination resolves its connection through the same control model every other command reads [`loadControl`], so a `deny: remote` still wins, and it PREFLIGHTS before the first request: a missing connection or a read-only `lk_ro_*` token fails in one line rather than mid-push, a write-only `lk_wo_*` token warns and then pushes WITHOUT classifying (its reads are denied, so asking would 403 every entry — the hosted upsert is idempotent either way), and an unrecognized prefix warns and proceeds so a self-hosted token still works. `--endpoint`/`--token` override the resolved connection, which `withOverrides` alone cannot carry because `resolveProjectConnection` reads `process.env` directly. **Fidelity is bounded by what the hosted write can express** — `scope`/`key`/`value`/`source_agent`/`trigger` transfer as the source states them [`value` is TRIMMED server-side by `MemoryWriteSchema`] and `created` travels as `created_at`, honoured on INSERT only, so a lesson NEW to the hosted store keeps its ranking recency while one already there keeps the date it has [and an unusable `created` is dropped for the write instant, reported as `createdAtDropped`]. Three fields are not verbatim in ways worth stating outright: `tags` are AUTHORITATIVE [`tags = excluded.tags`, so an untagged local entry CLEARS the hosted labels — the one field where a verbatim upsert removes hosted data], `origin_*` is STICKY [coalesced, so an entry carrying none leaves whatever the hosted row had, and no parameter overrides that], and `kind`/`host` are never sent [the server infers both from the `loop::` tag]. `updated` is re-stamped by the server and the `seen_count` tally is server-derived [migration 00059: a write IS the next sighting, so a key the hosted store already holds lands at ITS count plus one, not at 1], neither having a write parameter; `expires_at` converts to the remaining whole `ttl_days`, clamped to the schema's 1–365 — a clamp is lossy, so `putEntry` reports `ttlClamped` and the run NAMES each shortened entry, in the dry run as well as the apply. Idempotency therefore compares only what a write can change AND compares it the way the server stores it [`sameRemoteEntry`]: `value` trimmed, only the `origin_*` fields the SOURCE carries (the RPC coalesces provenance, so a local entry with none could never match a hosted row that has some), and an expiry that still HONOURS the local intent rather than matching its instant — the hosted one is fixed at push time while the local one is measured from now, so it is judged on whether at least half the intended life remains (`TTL_HONOURED_FRACTION`, the ask capped at the API maximum). Matching instants, or asking whether the hosted row outlives a freshly-computed intent, drifts with the clock and re-pushes forever; a genuinely SHORTER hosted TTL still does re-push. Each was a permanent-UPDATE loop before it was mirrored. A remote NOOP means "the hosted lesson already says this", not "byte-identical row". `tags` REPLACE the hosted labels and `origin_*` is sticky, so both are reported rather than implied, and every lossy outcome [clamped TTL, dropped `created`] is named per entry in the DRY RUN as well as the apply, computed by one shared `remoteWriteLosses` so a preview cannot promise what the apply does differently. Archived and expired entries are SKIPPED and counted, never pushed, because the hosted write inserts a SECOND live row beside an archived one rather than reviving it [every conflict predicate is partial on `archived_at is null`] and any TTL re-dates an expired row into the future. Both rate-limit guards are client-side [`src/store/rate-limit.mjs`]: a sliding-window pacer holds the run under a self-imposed 100/min below the server's 120/min — announcing itself the first time it waits, and re-paced on every retry attempt so the ceiling holds during the 429 episode it exists to prevent — and a 429 is still retried on the server's own `Retry-After` because the limit is per USER and a concurrent agent shares it. `isRetryable` also covers a 5xx and a transport error, the likeliest failure on a bulk push; a 4xx stays a decision. Widening it needed a bail-out, so five CONSECUTIVE failures abandon the run with a partial-progress report [reset by any success], rather than paying the full retry budget per entry through a systematic outage. The memory cap is translated to a 429 too, so it is told apart by `code: memory_cap` and treated as TERMINAL — the run stops, reports how many entries landed, and exits non-zero with guidance instead of retrying a write that cannot succeed. It reads LoreKit's own on-disk format only — not persistent-memory's `~/.agent-memory/<bucket>/` — and v1 has no `--org <slug>` org-owned write and no reverse remote→local direction), `archive`/`delete`/`restore` (aliases: `rm` → `delete`) (the removal lifecycle, the counterpart to `write` — `archive <scope::key>` soft-hides a lesson (reversible), `delete <scope::key> [--force]` soft-archives or hard-deletes with `--force`, `restore <scope::key>` un-archives. All three address a memory the same `<scope::key>` / `<scope> <key>` / `--scope`+`--key` way `write`/`list`/`show` do, and pick a store with `write`'s precedence [remote when usable else local, forced by `--remote`/`--local`]. Server-side they map to the hosted `memory.archive`/`memory.delete`/`memory.restore`, which are **scope-authorized for an API token by its allowlist** [migrations 00071/00072]: a key scoped to a scope may manage every writer's row in it, an unscoped key only its own, and a 0-row result is reported as not-found vs forbidden rather than a silent false), and `hook` (the shared hook engine behind the plugins — injects the ranked-then-**bucket-capped-then-MMR-diversified** top lessons on SessionStart [`sessionRankOpts` seeds a relevance query from the branch name (`branchQueryTerms` distils `scope.branch` after dropping the leading `type/`author segment; a trunk branch adds none; off via `hooks.sessionStart.branchHint: off`) at the DEFAULT relevance weight — it only LIFTS an on-topic lesson (a non-matching branch is byte-for-byte the old read), deliberately not damped by a smaller weight, which would shrink the score normaliser and distort the diversifier's MMR → `rankLessons` → `capPerBucket` (at most `hooks.sessionStart.loopCap` — default 1, `0` excludes loop buckets — per `loop::<bucket>` via `loopBucketOf`, so one prolific self-improvement loop cannot flood a general session; non-loop lessons uncapped) → `diversifyRankedLessons` applies the same `selectDiverse` λ=0.7 lexical-Jaccard pass the hosted `order=rank` path uses, so several near-identical iteration logs no longer take every slot. The block is bounded from BOTH directions — `hooks.sessionStart.maxChars` bounds its characters and `hooks.sessionStart.maxLessons` its LINE count (default 100, bounded 3–200, clamped not rejected); whichever binds first decides the block, and at the default budget that is almost always `maxChars`. **So `maxLessons` is a read-DEPTH dial, not a size one**: ONE resolved ceiling is spent on the fetch, the diversifier's `k` AND the render, and since the budget runs out around line 25 its working effect is the size of the candidate pool the ranker picks from. The pure `scopeReadLimit(maxLessons)` is `clamp(ceiling, SCOPE_READ_LIMIT, MAX_STORE_LIST_LIMIT)` — 100/scope by default (400 candidates across a four-scope hierarchy, versus the newest 25 before), never past `MAX_STORE_LIST_LIMIT = 100` (the `max(100)` on `ListMemoriesQuerySchema`, the schema validating `GET /memories` — NOT the `MemoryListSchema` MCP tool schema — mirrored self-contained per the `limits.ts` pattern, since an over-cap `limit` 400s and this best-effort path skips a failed scope, so the whole block would come back silently EMPTY), and never below `SCOPE_READ_LIMIT` so a lowered ceiling still ranks from a full pool. `HARD_LESSON_CEILING` survives as the absolute 200 clamp, applied a second time inside `core/lessons.mjs` because `fetchLessons`/`formatLessons` take `maxLessons` as a plain option that never passes through the config normaliser], **a per-turn relevance pull on UserPromptSubmit** [`promptQuery` distils terms from the prompt → `promptLessonsFromStore` ranks the store's hits and injects at most three the session has not already been shown, tracked by `core/state.mjs`'s append-only shown-set; gated by `hooks.userPrompt` (`on` default | `off`) and run under `PROMPT_FETCH_TIMEOUT_MS` rather than `restFetch`'s 10s default, because it sits on the user's critical path], **relevant lessons + a write-nudge on a tool failure** [`failureQuery` → `relevantLessonsFromStore` QUERIES the store — ONE `store.search` carrying all terms (OR) across the scope hierarchy, deduped/capped by the pure `dedupeRelevant` — not a post-filter of the injected set], and a **friction-gated** retrospective nudge on Stop [`hooks.stop`: `friction` default | `always` | `off`; `core/friction.mjs`'s `detectFriction`/`shouldRetrospect` read the transcript and stay silent on a clean session]; always exit 0, best-effort, never blocks the host), and `mcp` (a hand-rolled local stdio MCP server exposing `memory.*` from the resolved store — lets `.mcp.json` point at the CLI instead of `mcp-remote`, for offline local-mode tool calls). Ships three skills under `skill/*` — `lorekit-memory` (runtime read/write), `lorekit-setup` (authoring a self-improvement loop into a host), and `lorekit-groom` (a propose-then-confirm grooming pass over an accumulated store: survey→lint→dedupe/merge→expiry→prune, analysis via the CLI read commands and mutation via the `lorekit archive`/`delete`/`restore` commands or the `memory.*` MCP tools); `install`/`uninstall`/`doctor` iterate the `SKILLS` list in `config.mjs`, and `scripts/sync-plugin-skill.mjs` mirrors every `skill/*` into the plugin. Human-facing commands (`install`/`uninstall`/`doctor`/`list`/`search`/`show`/`stats`/`scopes`/`diff`/`tree`/`lint`/`dedupe`/`link`/`migrate`/`archive`/`delete`/`restore`) emit one OTel span + counter point per run via a zero-dep self-contained OTLP/JSON `fetch` exporter (`src/telemetry.mjs`, the `_shared/otel.ts` pattern) — `service.name=cli`, `service.namespace=lorekit`, no-PII attrs, opt-out via `LOREKIT_TELEMETRY`/`DO_NOT_TRACK`; `hook`/`mcp` stay uninstrumented. The ingesting-only Dash0 token is never committed — `src/telemetry-token.mjs` is empty in git and injected at publish time from the `LOREKIT_TELEMETRY_TOKEN` secret by `scripts/inject-telemetry-token.mjs` (wired into `release.yml`'s `publish-cli` job); `LOREKIT_TELEMETRY_TOKEN`/`OTEL_EXPORTER_OTLP_HEADERS` env override it at runtime. Verified by its own `node:test` suite; excluded from the NX TS lint gate.
